This page shows how to run Platform in production. You build a Docker image, prepare the database, and start the server behind a reverse proxy.
For every setting, see [Configuration](/docs/configuration).

---

## What you need

- A Linux server with Docker and Docker Compose.
- A domain name for Platform, such as `api.example.com`, and a TLS certificate for it.
- An OpenID Connect provider, such as `https://id.example.com`. Register a client with the redirect URI `https://api.example.com/auth/callback/oidc`.
- A model service, if you want the Agent to do work. See [Models](/docs/models).

## Build the images

All Docker files are in `deploy/docker/`. One `Dockerfile` makes both images. Each image is a build target (a named last stage in the file):

| Target          | Image                   | What it runs                                                                     |
| --------------- | ----------------------- | -------------------------------------------------------------------------------- |
| `platform`      | `openbot-platform`      | Platform and its migration program.                                              |
| `protocol-test` | `openbot-protocol-test` | The test service for the App Protocol. See [Protocol test](/docs/protocol-test). |

The file `docker-bake.hcl` tells [Docker Bake](https://docs.docker.com/build/bake/) how to build them. Run this from the root of the repository:

```sh
export OPENBOT_RELEASE=$(git rev-parse HEAD)
TAG=$OPENBOT_RELEASE docker buildx bake -f deploy/docker/docker-bake.hcl --load
```

This builds `openbot-platform:$OPENBOT_RELEASE` and `openbot-protocol-test:$OPENBOT_RELEASE` for `linux/amd64`. `--load` puts them in your local Docker. Without `TAG`, the tag is `local`. To build only one image, add its target name, for example `platform`.

On a computer that is not `x86_64`, Docker needs QEMU (a program that runs code for another processor) to build the images. Install it once with `docker run --privileged --rm tonistiigi/binfmt --install amd64`.

Both images start from [distroless](https://github.com/GoogleContainerTools/distroless), with the same Node.js version as development. Distroless images have no shell and no package manager, so you cannot `docker exec` a shell in them. They run as the user `nonroot` (65532).

The Platform image has Node.js, the bundled server, the bundled migration program, and the database migrations. It has no build tools and no secrets.

| Path in the image           | What it is                                       |
| --------------------------- | ------------------------------------------------ |
| `/app/dist/app/Main.mjs`    | The server. The image runs it by default.        |
| `/app/dist/app/Migrate.mjs` | The migration program. It prepares the database. |
| `/app/migrations`           | The database migrations.                         |

The server in the image listens on `0.0.0.0:3000`. The image has a health check that calls `/health` every five seconds.

### Secrets as files

Platform reads each setting from an environment variable first. When the variable is not set, Platform reads the file `/run/secrets/<NAME>` instead, for example `/run/secrets/BETTER_AUTH_SECRET`. This is where Docker and Compose put secrets. An empty file counts as not set. See [Configuration](/docs/configuration#secrets-as-files).

Environment variables show in `docker inspect`. Files in `/run/secrets` do not. Compose uses files for all secrets.

## Run with Docker

Put your settings in a file, for example `platform.env`. Start from `deploy/docker/production.env.example`. `docker run` does not fill in `${POSTGRES_PASSWORD}`, so write the full `OPENBOT_DATABASE_URL` yourself.

<Steps>
<Step>

### Prepare the database

The migration program only needs `OPENBOT_DATABASE_URL`. Run it before you start the server, and again before each new release:

```sh
docker run --rm --env-file platform.env \
  openbot-platform:$OPENBOT_RELEASE /app/dist/app/Migrate.mjs
```

It is safe to run it more than once. It only applies the migrations that the database does not have yet.
Migrations only go forward. There is no way to undo one, so make a backup first.

</Step>
<Step>

### Start the server

```sh
docker run -d --name openbot --env-file platform.env \
  -p 127.0.0.1:8080:3000 openbot-platform:$OPENBOT_RELEASE
```

When the server starts, it checks that the database has all tables. If not, it stops and you see an error in the log.

</Step>
<Step>

### Check it

```sh
curl http://127.0.0.1:8080/health
```

```json
{ "status": "ok" }
```

`/health` only shows that the HTTP server can answer. It does not check the database or the model.

</Step>
</Steps>

### Without Docker

You can also run the programs with Node.js on the server:

```sh
pnpm install --frozen-lockfile
pnpm --filter-prod @openbot-build/platform... build
pnpm --filter @openbot-build/platform migrate
pnpm --filter @openbot-build/platform start
```

The package `@openbot-build/platform` also has the commands `openbot-platform-migrate` and `openbot-platform`.

## Run with Compose

The file `deploy/docker/compose.production.yaml` runs these services:

| Service         | Image                                               | Port on the host                              |
| --------------- | --------------------------------------------------- | --------------------------------------------- |
| `postgres`      | `postgres:18-alpine`, data in the volume `postgres` | none                                          |
| `migrate`       | `openbot-platform:$OPENBOT_RELEASE`                 | none                                          |
| `platform`      | `openbot-platform:$OPENBOT_RELEASE`                 | `127.0.0.1:8080`, or `OPENBOT_PUBLISHED_PORT` |
| `protocol-test` | `openbot-protocol-test:$OPENBOT_RELEASE`            | `127.0.0.1:3001`                              |

`migrate` runs the migration program once, after PostgreSQL is healthy. `platform` starts only when `migrate` succeeds. So `up` always migrates the database first.

The `protocol-test` service is the public test service for the App Protocol. See [Protocol test](/docs/protocol-test).
The file needs `PROTOCOL_TEST_PUBLIC_ORIGIN` even if you only use Platform.

Compose gives the secrets to the containers as files in `/run/secrets`, not as environment variables. These are `POSTGRES_PASSWORD`, `OPENBOT_DATABASE_URL`, `BETTER_AUTH_SECRET`, `OPENBOT_APP_ENCRYPTION_KEY`, `OPENBOT_OIDC_CLIENT_SECRET`, `OPENBOT_MODEL_API_KEY`, `OPENBOT_LARK_WEBHOOK_URL`, and `OPENBOT_LARK_SIGNING_SECRET`. Compose takes their values from `.env.production`. The `migrate` service gets only `OPENBOT_DATABASE_URL`.

In the template, `OPENBOT_DATABASE_URL` uses `${POSTGRES_PASSWORD}`, so you set the password only once. Compose also sets `OPENBOT_ENVIRONMENT=production` and `OPENBOT_VERSION=$OPENBOT_RELEASE`.

<Steps>
<Step>

### Prepare the settings

```sh
cp deploy/docker/production.env.example .env.production
openssl rand -hex 32   # use the output for POSTGRES_PASSWORD
openssl rand -hex 32   # use the output for BETTER_AUTH_SECRET
openssl rand -hex 32   # use the output for OPENBOT_APP_ENCRYPTION_KEY
```

Fill in the values in `.env.production`.

</Step>
<Step>

### Build both images

```sh
export OPENBOT_RELEASE=$(git rev-parse HEAD)
TAG=$OPENBOT_RELEASE docker buildx bake -f deploy/docker/docker-bake.hcl --load
```

</Step>
<Step>

### Check the settings

```sh
docker compose --env-file .env.production -f deploy/docker/compose.production.yaml config --quiet
```

This shows an error when a required setting is missing. Without `--quiet`, it prints the full setup with all values filled in.

</Step>
<Step>

### Start everything

```sh
docker compose --env-file .env.production -f deploy/docker/compose.production.yaml up -d --wait
```

`--wait` returns when all services are healthy. The images check their health every five seconds. When a service process stops, Compose starts it again.

</Step>
</Steps>

To release a new version, build new images, set the new `OPENBOT_RELEASE`, back up the database, and run `up -d --wait` again. `migrate` runs again before the new Platform starts.
Never delete the `postgres` volume. It holds all your data.

## TLS and the reverse proxy

In production, a reverse proxy handles HTTPS and sends the traffic to Platform on `127.0.0.1:8080`.
Leave `OPENBOT_TLS_CERT` and `OPENBOT_TLS_KEY` empty.

The proxy must:

- send the `Origin`, `Cookie`, and `Authorization` headers to Platform without changes,
- not buffer responses, because Turns can stream their output as server-sent events (SSE),
- allow long responses. `GET /v1/sessions/:id/wait` can wait for up to 30 seconds, and a stream lasts as long as its Turn.

<Tabs items={["nginx", "Caddy"]}>
<Tab value="nginx">

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;
    ssl_certificate /etc/ssl/api.example.com.pem;
    ssl_certificate_key /etc/ssl/api.example.com.key;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header Connection "";
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 1h;
    }
}
```

</Tab>
<Tab value="Caddy">

```txt
api.example.com {
    reverse_proxy 127.0.0.1:8080 {
        flush_interval -1
    }
}
```

</Tab>
</Tabs>

## Your own client on the same origin

A browser client on the same origin as Platform can use the sign-in cookie. It needs no user token.
To do this, your proxy sends some paths to Platform and all other paths to your client.

| Path            | Send to     | What it is                                             |
| --------------- | ----------- | ------------------------------------------------------ |
| `/auth/*`       | Platform    | Sign-in, sign-out, and the App authorization callback. |
| `/v1/*`         | Platform    | The API.                                               |
| `/health`       | Platform    | The health check.                                      |
| `/openapi.json` | Platform    | The OpenAPI document.                                  |
| `/docs`         | Platform    | The interactive API reference. Optional.               |
| everything else | Your client | Your pages, including `/`.                             |

When you mount your client at `/`, the service document of `GET /` is no longer public. That is fine. Clients can use the paths above directly.

After sign-in, Platform sends the browser back to a path on your client. The default is `/`. Your client must also handle these return addresses:

- `/?authorization=<flowId>` after an App authorization. Call `completeAppAuthorization` next. See [Apps](/docs/apps).
- `/?developerTest=<testId>` after a developer test authorization. See [Developer tools](/docs/developer-tools).

A return path can be any path on the same origin, except paths under `/auth/`, `/v1/`, and `/development/`.

## Backups

Back up two things, and keep them together:

1. **The database.** It holds accounts, the organization and its members, user tokens, the audit log, Sessions and their Timelines, and App connections.
2. **The secrets file.** `OPENBOT_APP_ENCRYPTION_KEY` decrypts App secrets in the database. A database backup without this key cannot restore App connections. Also keep `BETTER_AUTH_SECRET`, or everyone must sign in again.

With Compose, make a database backup like this:

```sh
docker compose --env-file .env.production -f deploy/docker/compose.production.yaml \
  exec -T postgres pg_dump -U openbot -Fc openbot > openbot-$(date +%F).dump
```

To restore it, first stop Platform with `docker compose --env-file .env.production -f deploy/docker/compose.production.yaml stop platform`. Then run `pg_restore`:

```sh
docker compose --env-file .env.production -f deploy/docker/compose.production.yaml \
  exec -T postgres pg_restore -U openbot -d openbot --clean < openbot-2026-10-20.dump
```

## GitHub Actions

The workflow `.github/workflows/ci.yml` has two jobs. The second job runs only when the first one passes.

| Job      | What it does                                                               |
| -------- | -------------------------------------------------------------------------- |
| `check`  | Runs `pnpm build`, `pnpm typecheck`, and `pnpm -r test` in `devenv shell`. |
| `images` | Builds, checks, scans, and publishes the Docker images.                    |

Both jobs run on `ubuntu-latest`. They install Nix with the Determinate Nix installer, and then devenv 2.4.0. [Magic Nix Cache](https://github.com/DeterminateSystems/magic-nix-cache-action) keeps Nix build results in the GitHub Actions cache, so later runs do not build them again. The jobs also download prebuilt devenv packages from `devenv.cachix.org`. The `check` job keeps the pnpm store in a cache.

The `images` job does these steps:

1. [hadolint](https://github.com/hadolint/hadolint) and `docker buildx bake lint` check the `Dockerfile`. The second one runs the [Docker build checks](https://docs.docker.com/build/checks/).
2. Docker Bake builds both images. Build layers stay in the GitHub Actions cache, with one cache for each image, so later runs build only what changed.
3. `deploy/docker/check.sh` checks the images. See [Check the images](#check-the-images).
4. [dive](https://github.com/wagoodman/dive) checks that the image layers do not waste space.
5. [Trivy](https://trivy.dev) scans both images. The job fails when an image has a known `HIGH` or `CRITICAL` vulnerability that has a fix. Trivy does not see the Node.js version, because Node.js is copied into the image and not installed as a package.
6. The job saves both images as the `images-<commit-sha>` artifact for seven days.
7. For pushes, the job publishes the images. It uses the build cache, so it does not build again.

The workflow runs for pull requests, pushes to `main`, and tags like `v1.2.3`. It publishes images only for pushes:

| Event               | Published tags              |
| ------------------- | --------------------------- |
| A push to `main`    | `<commit-sha>` and `latest` |
| A tag like `v1.2.3` | `<commit-sha>` and `v1.2.3` |

The images go to the GitHub container registry, at `ghcr.io/openbot-build/openbot/platform` and `ghcr.io/openbot-build/openbot/protocol-test`. The workflow does not deploy. To use a published image with Compose, pull it and tag it as `openbot-platform:<tag>`.

### Check the images

`deploy/docker/check.sh` starts `compose.production.yaml` with test settings. The extra file `compose.check.yaml` removes the host ports and adds a `check` service. `check.env` has the test settings. None of them are real secrets.

The `check` service runs `check.mjs` inside the Compose network, after Platform and the protocol test service are healthy. It checks that:

- `/v1/sessions` returns `401` with no key and with a bad key,
- `/openapi.json` works,
- the protocol test Catalog has the right public origin,
- MCP discovery on the protocol test service works.

So the check also proves that migrations, secret files, and health checks work in the real production setup. At the end, the script removes the containers and the test database.

Run the same checks on your computer:

```sh
devenv shell -- pnpm images
devenv shell -- pnpm images:check
devenv shell -- hadolint deploy/docker/Dockerfile
devenv shell -- dive --ci --source docker openbot-platform:local
devenv shell -- trivy image --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed openbot-platform:local
```
