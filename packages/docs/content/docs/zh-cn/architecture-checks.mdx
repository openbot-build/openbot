本页将[执行设计](/zh-cn/architecture)对应到源代码测试和发布检查。源码核对日期为 2026-10-28。这里列出的测试是**源码证据，不是测试通过记录**。每次发布检查应记录版本、命令、结果和日志。命令和测试服务的限制见
[端到端检查](/zh-cn/developers/testing)。

## 如何阅读本表

测试分布在各源码包和 `packages/e2e`
中。测试数量增加，不能证明每种行为都保留。测试移动或删除时，应在新位置保留它的断言，或写下已获准的行为变更。

`packages/e2e/scenarios.json`
详细记录用户任务的断言。它包含 22 个任务组，区分正常、边界和极端场景。空列表不表示已覆盖。本页补充统一执行检查。

表中使用以下路径前缀：

- `E/` 表示 `packages/e2e/test/`。
- `S/` 表示 `packages/server-testing/test/`。
- 其他路径从项目根目录开始。

测试可能使用真实数据库和固定模型回复，也可能使用真实 HTTP 服务和测试工作流，或完整服务器。这些测试的范围不同。服务 Layer 重启不等于进程崩溃。同一进程中的两个服务对象也不等于两个服务器进程。

`scripts/effect-rules.ts` 检查 `domain-boundary`、
`storage-contract-boundary`、`standalone-boundary`、`execution-boundary` 和
`public-entry`。`pnpm typecheck`
运行这些规则。它们检查导入关系，本身不能找出所有第二套执行器或恢复循环。新增 worker、计时器、锁和 RPC
handler 仍需按统一设计审查。 `storage-contract-boundary` 和 `execution-boundary`
只检查
`src`。测试像客户端一样调用 HTTP 合约。测试也可以启动集群或本地 Chat 运行时，来建立它要检查的环境。这不是服务器工作。`packages/server-testing/src`
里的辅助工具也是测试代码，所以规则把它们当作测试来检查。

另外四条规则保护插件宿主。`graft-boundary` 只允许插件工具包（`server-plugin`
包）、每个插件包的 `src/index.ts`
文件、宿主（`packages/openbot/src`）、宿主和插件工具包的测试，以及
`server-testing` 的辅助工具和测试导入 graft。开发服务器使用
`Host.layer`，所以它不导入 graft。它还要求把 graft 的 `Plugin` 命名为
`GraftPlugin`。`feature-lookup` 不允许服务器包的代码和测试用
`Effect.serviceOption` 或 `Plugin.optional`
查找功能。代码应列出它需要的服务。`kernel-provide`
不允许插件发布内核的服务。插件只发布契约包（`*-contract`
包）、`api`、`domain`、`protocol` 或它自己的包中的键。宿主从它自己的包发布
`Wallets`。preset 的一个测试也检查没有插件发布内核的键。`host-only`
只允许宿主、`server-kernel` 的 HTTP 文件和 `server-execution` 用
`HttpRouter.serve` 或 `HttpRouter.toWebHandler` 提供 HTTP 服务、用
`HttpApiBuilder.layer` 构建 HTTP
API、添加全局 HTTP 中间件，或者用工作流构建 layer。插件用 `HttpHost`
挂载自己的路由，用 `Workflows.contribute` 提供自己的工作流。

`package-layer` 让各包分层。包的名字说明它的种类，所以规则不需要包的列表：
`server-*`、`*-contract`、`model-providers` 和 `plugin-*` 是服务器包，`plugin-*`
是插件。`core`、`domain`、`protocol` 和 `api`
是基础层。基础层之上从低到高依次是：`server-database`、`server-kernel`、`server-billing`、`server-execution`、`identity-contract`、`tools-contract`、`models-contract`、`apps-contract`、`conversation-contract`、`model-providers`、`server-plugin`，然后是插件包（`plugin-<id>`），然后是宿主（`openbot`），然后是
`server-development`，然后是
`server-testing`。包只能导入更低的层。基础层的包不导入服务器包，`server-database`
只使用 `core` 和 `domain`。`domain-boundary` 和 `standalone-boundary`
检查基础层各包之间的导入。`public-entry` 只允许其他包通过服务器包或宿主
`package.json` 中 `exports` 的键来使用它。测试也是这样。

两条规则让插件彼此分开。`plugin-boundary`
不允许一个插件导入另一个插件。插件包和它们的测试都是这样。宿主通过 graft 连接各个插件。`plugin-entry`
检查插件包的 `src/index.ts`
只有一个导出：插件本身，作为默认导出。每个插件包的入口测试检查它的
`package.json` 不包含其他插件包。worker 文件是它所在包的构建入口，但不是
`exports` 中的键，因为它一加载就开始工作。`plugin-code` 的 Code Mode
worker 就是这样的文件。

四条规则让名字和路径保持简单。每条规则都在消息中给出期望的值，所以修正就是复制。

- `identity-key`：服务、引用、中间件或符号的键是
  `@openbot-build/<包>/<模块路径>`；当类或 `const` 的名字不是模块名时，再加上
  `/<名字>`。测试模块使用同样的规则，路径中带 `test/`。品牌（brand）是
  `@openbot-build/<包>/<名字>`。关闭 `deterministicKeys`
  检查的文字也是一个发现，并且 `tsconfig.base.json`
  把 Effect 语言服务的这项检查设为 `error`。这样语言服务和规则要求同一个键。
- `package-layout`：包把模块平放在 `src`
  中。只有多个插件的契约包有文件夹，每个插件一个文件夹，以插件 id 命名。`exports`
  的每个键指向由 `src/<路径>.ts` 构建的
  `dist/<路径>.js`，所以模块的导入路径、文件和键一致。
- `no-reexport`：模块不再次导出工作区中其他包的符号，也不给符号第二个名字。第二个名字是一个导出的常量或类型，它的整个值是一个导入的名字，例如
  `X.member`。从同一个包的另一个模块导入的名字也是这样。只有 `packages/client`
  的打包入口导出其他包的代码。
- `unused-entry`：只有当另一个包导入某个键，或文档页的代码示例展示它时，服务器包或宿主才在
  `exports` 中有这个键。插件的 `.`
  键保留，因为宿主按名字加载插件。来自同一个包（包括它的测试）的导入不算数。测试通过源文件路径导入自己包中没有键的模块。

## 发布证据

在同一个固定版本上运行[项目检查](/zh-cn/developers/testing)。先完成构建，再开始测试，因为测试和子进程会加载构建文件。

| 检查           | 入口                                                                 | 所需证据                                                                              |
| -------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 构建与类型     | `devenv shell -- pnpm build`; `devenv shell -- pnpm typecheck`       | 全部包、包测试脚本中的测试类型检查及依赖规则。                                        |
| 包和用户任务   | `devenv shell -- pnpm -r test`                                       | 完整测试输出、跳过项目和最终 E2E 断言表。                                             |
| 故障与迁移     | 上面的 F01–F11 和 A01–A04                                            | 进程边界、故障点、终态、外部动作次数及保存的事件/调用证据。                           |
| 镜像与 Compose | `.github/workflows/ci.yml`, `deploy/docker/check.sh`                 | Docker 构建检查、Compose 启动/迁移/API 检查、镜像层检查和对应镜像 ID 的漏洞扫描输出。 |
| 文档           | 文档包构建、`E/read-docs/Docs.test.ts`、`.github/workflows/docs.yml` | 英语、中文、德语、生成的 API 参考和链接检查。                                         |
| 合并与推送     | 合并后精确版本的 CI                                                  | 必需任务通过。本地局部测试或较早快照不是最终 CI 证据。                                |

发布检查应以精确发布提交的 CI 为准，包括镜像、Compose、扫描及文档。本地测试证据不能替代这些任务。
