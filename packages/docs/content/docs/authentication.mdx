This page shows how people sign in to OpenBot and how programs call the API.
A person signs in once in a browser. Then the person creates user tokens for scripts and services.

There are two ways to call the business routes under `/v1`:

| Way            | Who uses it                            | What you send                       |
| -------------- | -------------------------------------- | ----------------------------------- |
| User token     | Scripts, backend services, bots        | `Authorization: Bearer <token>`     |
| Session cookie | A browser client on the OpenBot origin | The `__Host-openbot-session` cookie |

Both ways need a permission for each call. See [Permissions](/docs/permissions).

---

## Sign in

OpenBot does not keep passwords. It uses an OpenID Connect provider. OpenID Connect (OIDC) is a standard way to let another service check who a person is.

OpenBot uses [Better Auth](https://better-auth.com) for sign-in. Better Auth serves all of its routes under `/auth/*`, as its [Effect guide](https://better-auth.com/docs/integrations/effect) shows. These routes are not in the API reference. The [Better Auth docs](https://better-auth.com/docs/concepts/api) describe them.

To start a sign-in, your client sends this request from the OpenBot origin:

```sh
curl -X POST https://api.example.com/auth/sign-in/social \
  -H "Origin: https://api.example.com" \
  -H "Content-Type: application/json" \
  -d '{ "provider": "oidc", "callbackURL": "https://api.example.com/settings/keys" }'
```

The answer is JSON with a `url`. Send the browser to that `url`. After the person signs in, the provider sends the browser back to `https://api.example.com/auth/callback/oidc`. Better Auth then sets the session cookie and sends the browser to `callbackURL`. The `callbackURL` must be on the OpenBot origin. If it is not, Better Auth returns `403`.
If the sign-in fails, Better Auth sends the browser to `/auth/error?error=<code>` and sets no cookie.

### Set up the provider

Register OpenBot as a client at your provider. Then set these environment variables:

| Variable                     | Value                                                                           |
| ---------------------------- | ------------------------------------------------------------------------------- |
| `OPENBOT_OIDC_ISSUER`        | The issuer URL, for example `https://id.example.com`. HTTPS, no trailing slash. |
| `OPENBOT_OIDC_CLIENT_ID`     | The client ID from the provider.                                                |
| `OPENBOT_OIDC_CLIENT_SECRET` | The client secret. Leave it empty for a public client.                          |
| `OPENBOT_PUBLIC_ORIGIN`      | The public HTTPS origin of OpenBot, for example `https://api.example.com`.      |

Use `<origin>/auth/callback/oidc` as the redirect URI at the provider. OpenBot asks for the scopes `openid profile email`.
With an empty client secret, OpenBot signs in as a public client with PKCE. PKCE is a check that protects the sign-in code.

### Development account

For local work, set `OPENBOT_DEV_MODE=1`. OpenBot then uses one local account named "Local Developer" and no provider.
This mode works only when the public origin is HTTPS on a loopback host: `localhost`, `127.0.0.1` or `[::1]`.

This command signs in and saves the cookie in a file:

```sh
curl -c cookies.txt -X POST https://localhost:8443/auth/development/sign-in \
  -H "Origin: https://localhost:8443" \
  -H "Content-Type: application/json" \
  -d '{}'
```

### Read and end the sign-in

`GET /auth/session` returns the signed-in account. It needs the session cookie. `organizationId` is the ID of the organization.

```json
{
	"identity": { "userId": "u_123", "organizationId": "org_8f3a" },
	"profile": {
		"name": "Ada",
		"email": "ada@example.com",
		"emailVerified": true
	},
	"expiresAt": "2026-11-19T10:00:00.000Z"
}
```

`POST /auth/sign-out` ends the sign-in. It is a Better Auth route. Send a JSON body (`{}`) and the `Origin` header (see below). It returns `200`.

## Membership

Every account that signs in must be a member of the organization. One deployment has one organization. See [Organization](/docs/organization).

- The first account that signs in creates the organization and becomes a Super Administrator. This is also how one person uses OpenBot alone.
- An account with a verified email in an allowed email domain joins as a member.
- Other accounts get `403` with `MembershipRequired`. An administrator must allow their email domain first.
- A suspended member gets `403` with `MembershipRequired` when they use the cookie. Their tokens stop working at once and get `401` with `AuthenticationRequired`.

## The session cookie

After sign-in, the browser holds the cookie `__Host-openbot-session`. It is `Secure`, `HttpOnly` and `SameSite=Lax`.

- A sign-in lasts 30 days.
- OpenBot renews it after one day of use.

### The Origin rule

A cookie goes with every browser request, even from other sites. So OpenBot checks where a write comes from.
When you use the cookie, every `POST`, `PUT`, `PATCH` and `DELETE` request must send an `Origin` header.
The header must be exactly equal to `OPENBOT_PUBLIC_ORIGIN`. If it is not, OpenBot returns `403` with `ForbiddenOrigin`.

```sh
curl -b cookies.txt \
  -H "Origin: https://localhost:8443" \
  -H "Content-Type: application/json" \
  -d '{"title":"Notes"}' \
  https://localhost:8443/v1/sessions
```

Requests with a user token do not need the `Origin` header.

## User tokens

A user token lets a program act for you. A token can never do more than you can do. It can also have its own policies, so it does less. See [Permissions](/docs/permissions).

You can manage tokens with the session cookie, or with a token that has the `tokens.write` permission. A token made without policies cannot manage tokens.

See the full shapes in the [User tokens reference](/docs/api/operations/tags/user-tokens/).

### Create a token

```sh
curl -b cookies.txt \
  -H "Origin: https://api.example.com" \
  -H "Content-Type: application/json" \
  -d '{"name":"CI bot","expiresInDays":90}' \
  https://api.example.com/v1/user/tokens
```

| Field           | Rules                                                                                                                               |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `name`          | Required. 1 to 80 characters after trimming spaces.                                                                                 |
| `expiresInDays` | Optional. A whole number from 1 to 365. Leave it out for a token that works until you revoke it.                                    |
| `policies`      | Optional. Policies that limit the token. Leave it out to allow everything that you can do, except `tokens.read` and `tokens.write`. |

OpenBot returns `201`:

```json
{
	"token": {
		"id": "5f0c2a8e-7d1b-4c3e-9a55-2b6f1e8d4c10",
		"name": "CI bot",
		"prefix": "obut_Xr4pQ2aL",
		"policies": [
			{
				"effect": "allow",
				"permissionGroups": [
					"responses.run",
					"sessions.read",
					"sessions.write"
				],
				"resources": ["openbot.org.{org}"]
			}
		],
		"createdAt": "2026-10-20T09:00:00.000Z",
		"expiresAt": "2027-01-18T09:00:00.000Z",
		"lastUsedAt": null
	},
	"secret": "obut_Xr4pQ2aL..."
}
```

<Callout type="warn">
	OpenBot shows the `secret` only once. Save it now in a safe place. OpenBot
	keeps only a SHA-256 hash of it.
</Callout>

Every secret starts with `obut_`, so a leaked token is easy to spot. The `prefix` is the first 13 characters. Use it to tell your tokens apart.

### List tokens

```sh
curl -b cookies.txt https://api.example.com/v1/user/tokens
```

The answer is `{ "items": [ ... ] }`, oldest first. The list never contains secrets.
`lastUsedAt` changes at most once a minute. Expired tokens stay in the list until you revoke them.

### Revoke a token

```sh
curl -X DELETE -b cookies.txt \
  -H "Origin: https://api.example.com" \
  https://api.example.com/v1/user/tokens/5f0c2a8e-7d1b-4c3e-9a55-2b6f1e8d4c10
```

OpenBot returns `204` and deletes the token. The token stops working at once.

### Check a token

`GET /v1/tokens/verify` shows who the caller is. For a token, it also shows the token and its policies. Every caller can use it.

```json
{
	"caller": {
		"kind": "user_token",
		"userId": "u_123",
		"organizationId": "org_8f3a",
		"tokenId": "5f0c2a8e-7d1b-4c3e-9a55-2b6f1e8d4c10"
	},
	"token": { "id": "5f0c2a8e-7d1b-4c3e-9a55-2b6f1e8d4c10", "name": "CI bot" }
}
```

With the session cookie, `caller.kind` is `member` and `token` is `null`.

### Limits and errors

| Status | Error                     | When                                                      |
| ------ | ------------------------- | --------------------------------------------------------- |
| `400`  | `TokenPolicyInvalid`      | A policy names a resource outside your organization.      |
| `401`  | `AuthenticationRequired`  | No valid cookie or token.                                 |
| `403`  | `PermissionDenied`        | The caller does not have `tokens.read` or `tokens.write`. |
| `403`  | `ForbiddenOrigin`         | A cookie write without the exact `Origin` header.         |
| `404`  | `TokenNotFound`           | You have no token with this ID.                           |
| `409`  | `TokenLimitReached`       | You already have 25 tokens. The body has `"limit": 25`.   |
| `503`  | `TokenStorageUnavailable` | OpenBot cannot reach its database.                        |

A member can hold 25 tokens at a time. Expired tokens count too, so revoke old tokens to make room.

## Use a token

Send the token in the `Authorization` header on any `/v1` route:

```sh
curl -H "Authorization: Bearer $OPENBOT_TOKEN" \
  https://api.example.com/v1/sessions
```

A revoked, expired or unknown token gets `401` with `AuthenticationRequired`. If OpenBot cannot check the token, it returns `503` with `AuthenticationUnavailable`.

### Your own space

Inside the organization, each member has their own Sessions, Apps and connections. Your tokens and your cookie see only your own.
If you ask for a Session of another member, OpenBot answers `404`, as if it does not exist.

## Return paths

Some flows send the browser back to your client after a round trip. You choose the place with `returnTo`.

A return path must be a path on the same origin. It must start with one `/`. It cannot point to `/auth/*`, `/v1/*` or `/development/*`, because OpenBot owns those paths. The default is `/`.

OpenBot has no pages, so your client must serve these paths. Two flows add a query value:

- **App authorization.** When an App sign-in comes back and the person is signed in, OpenBot finishes the flow. The browser goes to the return path with `?authorization=<flowId>`. Your client can read the result with `GET /v1/app-authorizations/<flowId>`.
  If the person is not signed in, the browser goes to `/?authorization=<flowId>`. Your client signs the person in with Better Auth (see [Sign in](#sign-in)), with this address as `callbackURL`. Then it calls `POST /v1/app-authorizations/<flowId>/complete` to finish the flow.
- **Developer tests.** A developer test authorization returns to `/?developerTest=<testId>`.
