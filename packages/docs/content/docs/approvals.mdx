title: Approvals
description: Let a person approve or reject tool calls before they run.
---

Some tools can change things outside OpenBot, such as sending a message or making a booking. Before such a tool runs, the Turn stops and waits for a person to decide.
This page shows when a Turn waits, how to answer, and how Platform checks approvals for App tools.

---

## When a Turn waits

A tool can ask for approval. When the model calls such a tool, Platform does not run it. Instead:

- The Turn status becomes `WaitingApproval`.
- The Session summary status becomes `WaitingApproval`.
- The response status becomes `incomplete`. A stream ends with `response.incomplete`.

These tools ask for approval:

- Every App tool call, unless a read rule or a read grant covers it. See [App tool rules](#app-tool-rules).
- Any tool in your own Agent that sets `needsApproval`.
- In development, the `mock-tool` model calls a harmless tool that waits for approval. Use it to test your client.

The Turn waits as long as needed. You can still [interrupt](/docs/sessions#steer-queue-and-interrupt) it.

## List approvals

```sh
curl -H "Authorization: Bearer $OPENBOT_API_KEY" \
  https://api.example.com/v1/sessions/$SESSION/approvals
```

```json
[
	{
		"turn": "t-19aa",
		"approvalId": "ap-01",
		"toolCallId": "call-01",
		"toolName": "DevelopmentConfirmation",
		"arguments": { "description": "Confirm the test step" }
	}
]
```

| Field        | Meaning                                             |
| ------------ | --------------------------------------------------- |
| `turn`       | The Turn that waits.                                |
| `approvalId` | The ID you use to answer.                           |
| `toolCallId` | The ID of the model's tool call.                    |
| `toolName`   | The tool the model wants to use.                    |
| `arguments`  | The exact values the model wants to send.           |
| `app`        | Only for App tools. The saved App call (see below). |

Show the tool name and the arguments to the person before they decide.
The list is empty when the current Turn does not wait.

<Callout type="info">
	After a server restart, a waiting Turn cannot go on. The list is then empty
	and the Session `activity` is `historical`. Call `POST
	/v1/sessions/:sessionId/resume` to mark the Turn `Interrupted`, then start a
	new Turn.
</Callout>

## Answer an approval

```sh
curl -H "Authorization: Bearer $OPENBOT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"expected":7,"approved":true}' \
  https://api.example.com/v1/sessions/$SESSION/turns/t-19aa/approvals/ap-01
```

| Field        | Meaning                                                                           |
| ------------ | --------------------------------------------------------------------------------- |
| `expected`   | Required. The current `session.revision`.                                         |
| `approved`   | Required. `true` to run the tool, `false` to reject it.                           |
| `grantReads` | Optional. For App read tools only. See [Read grants](#read-grants).               |
| `reason`     | Optional text. Platform accepts it but does not store it or send it to the model. |

Platform returns `202` with the Turn's response in `status: "in_progress"`. The Turn goes on in the background. Read the result as you do for any Turn. See [Sessions](/docs/sessions#background-answer).

Answer one approval at a time. If the Turn stops for approval again, list the approvals again.

### Errors

| Status | Error                         | When                                                                                       |
| ------ | ----------------------------- | ------------------------------------------------------------------------------------------ |
| `409`  | `SessionConflict`             | `expected` is old, the Turn is not the current Turn, or the approval is no longer pending. |
| `409`  | `SessionConflict`             | The App connection changed or is off. Review the call again.                               |
| `503`  | `SessionExecutionUnavailable` | Platform has no model to go on with the Turn.                                              |

### What a rejection does

When you reject a call, the tool does not run. The model gets a tool result that says the call was denied. The Turn then goes on, and the model usually answers without that tool.
For an App tool, Platform marks the saved call `Rejected` and never contacts the App.

## App tool rules

An App is an outside service that a person connects to the account. See [Apps](/docs/apps). Platform is careful with App tools, because they act in the real world.

### What needs approval

| App capability                         | Approval                                              |
| -------------------------------------- | ----------------------------------------------------- |
| Tools                                  | Always, unless a read rule and a read grant cover it. |
| Resources, resource templates, prompts | None. Platform treats them as reads.                  |

Platform never trusts an App's own hints about which tools are safe.

### What an approval is bound to

Each App approval belongs to one exact call. Platform saves the call before it asks, and checks it again before it runs. An approval is bound to:

- the owner (your account),
- the Session,
- the Turn,
- the tool call ID,
- the exact `arguments`,
- the recipient: the App connection and its revision.

If the connection changes or is turned off before the call runs, the approval fails with `409`. A new revision of the connection never reuses an old approval.

The `app` field in the approval list shows the saved call. It has `id`, `toolName`, `arguments`, `readOnly`, `status` and `source`. `source` names the App (`appName`, `cardUrl`), the connection (`connectionId`, `connectionName`, `revision`) and the tool (`kind`, `name`). It never holds secrets.

### Read rules

A read rule marks one App tool as a read. A read only looks at data and does not change it. Each rule names a Card URL and a tool name:

```ts
{ cardUrl: "https://app.example.com/card.json", tool: "search_orders" }
```

Read rules come from the host that runs Platform, not from the App. A host that embeds Platform passes them as the `appReadRules` option. The standard server has no read rules, so every App tool call asks for approval.

### Read grants

When you approve a read tool, you can also send `"grantReads": true`. After that call completes, later calls of the same tool skip approval. This holds only in the same Session, on the same connection and the same connection revision.
`grantReads` has no effect on a tool that is not a read.
