A **Session** is one conversation and line of work. You give it work in **Turns**. A Turn is one request and all the Bot work that follows it. Every Session belongs to one [Bot](/docs/bots).
This page shows the Session and Turn routes. Every route is under `/v1/sessions` and accepts a user token or the session cookie. See [Authentication](/docs/authentication).

| Term          | Meaning                                                                                         |
| ------------- | ----------------------------------------------------------------------------------------------- |
| Item          | One record inside a Turn, such as a user message, a model answer, a tool call or a tool result. |
| Revision      | `session.revision`. A number that goes up with every change to the Session.                     |
| Timeline      | All saved Versions of a Session. Each change adds a new Version.                                |
| Timeline head | `session.head`. The ID of the current Version on the Timeline.                                  |
| Version       | A saved point in the history. A Version never changes after OpenBot saves it.                   |

Most writes need `expected`. This is the revision you last saw. If the Session changed since then, OpenBot returns `409` with `SessionConflict`. Read the Session again and retry.

## Create a Session

```sh
curl -H "Authorization: Bearer $OPENBOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title":"Trip plan"}' \
  https://api.example.com/v1/sessions
```

All fields are optional. `title` is a short name. OpenBot removes spaces at the start and end. The rest must have 1 to 100 characters. A Session without a title has no `title` field in its `metadata`. `bot` is the ID of the Bot that works in the Session. Without it, your [default Bot](/docs/bots#your-default-bot) works in it. If you have no default Bot, OpenBot returns `400` with `BotInvalid`. You need `bots.delegate` on the Bot. `settings` can hold `mode` and `model`. Without a model, the Session uses the model of the Bot. When neither gives a model, OpenBot returns `400` with `SessionModelInvalid` and the reason `missing`. There is no default model. See [Models](/docs/models#choose-a-model). To set the memory switches, see [Memory](/docs/memory#switches). Creating a Session does not call a model.
OpenBot returns `201` with the Session view. Here is a short form of it:

```json
{
	"session": {
		"id": "a41c9e0f",
		"revision": 0,
		"head": "v-7d21",
		"metadata": { "title": "Trip plan" },
		"settings": { "mode": "build" },
		"pending": [],
		"turns": [],
		"inheritedTurns": []
	},
	"state": {
		"version": { "id": "v-7d21" },
		"value": { "conversation": { "history": [] } }
	},
	"bot": "bot_3f9a…",
	"kind": "direct",
	"parent": null,
	"response": null,
	"activity": "inactive"
}
```

`bot` is the Bot of the Session. `kind` is `direct` for work that a client started, `delegated` for work that another Bot gave, `review` for a Session where a Bot decides one [request](/docs/requests), `trigger` for work that a [trigger](/docs/triggers) started, and `channel` for one chat of a [Channel](/docs/channels). `parent` names the Session, Turn and tool call that started delegated work. See [Delegation](/docs/delegation).

`response` is the latest Turn's answer. `activity` is `active` while a Turn runs on this server, `inactive` when nothing runs, and `historical` when a saved Turn says it runs but no server runs it.

## List and read Sessions

```sh
curl -H "Authorization: Bearer $OPENBOT_TOKEN" \
  "https://api.example.com/v1/sessions?archived=false"
```

The list is an array of summaries. Each summary has `session`, `bot`, `kind`, `parent`, `status` (`Idle`, `Running`, `Waiting`, `Completed`, `Failed` or `Interrupted`), `turn`, a short `response` and `activity`. Leave out `archived` to get all Sessions. Add `bot=<id>` to list the Sessions of one Bot. Review Sessions are left out unless you add `kind=review`.

`GET /v1/sessions/:sessionId` returns the full view. Reading never starts work.

To wait for a change, use a long poll. OpenBot answers when the revision is no longer `after`, or when the timeout ends. The longest wait is 30 seconds.

```sh
curl -H "Authorization: Bearer $OPENBOT_TOKEN" \
  "https://api.example.com/v1/sessions/$SESSION/wait?after=3&timeoutMs=30000"
```

## Rename, archive and delete

```sh
curl -X PATCH -H "Authorization: Bearer $OPENBOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"expected":3,"title":"Trip to Rome","archived":true}' \
  https://api.example.com/v1/sessions/$SESSION
```

`expected` is the current `revision` of the Session. `title` follows the same rules as when you create a Session. Send `"title": null` to remove the title. Leave out a field to keep its value.

`DELETE /v1/sessions/:sessionId` removes the Session and returns `204`. Its [Session Bots](/docs/bots#three-kinds-of-bots) are archived. If a Turn runs, OpenBot returns `409` with `SessionBusy`.

## Start a Turn

```sh
curl -H "Authorization: Bearer $OPENBOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"expected":0,"input":"Plan three days in Rome."}' \
  https://api.example.com/v1/sessions/$SESSION/turns
```

| Field        | Meaning                                                                          |
| ------------ | -------------------------------------------------------------------------------- |
| `expected`   | Required. The current `session.revision`.                                        |
| `input`      | Required. Text, or a list of user messages (see below).                          |
| `stream`     | Optional. `true` sends live events. See [Stream the answer](#stream-the-answer). |
| `background` | Optional. Only `true` is allowed. Every Turn runs in the background.             |
| `overrides`  | Optional. Settings for this Turn only: `mode` and `model`.                       |

`input` takes text only. These three forms are the same:

```json
"Plan three days in Rome."
```

```json
[{ "role": "user", "content": "Plan three days in Rome." }]
```

```json
[
	{
		"type": "message",
		"role": "user",
		"content": [{ "type": "input_text", "text": "Plan three days in Rome." }]
	}
]
```

Unknown fields return `400`.

### Background answer

Without `stream`, OpenBot returns `202` at once. The response has `status: "in_progress"`:

```json
{
	"id": "t-19aa",
	"object": "response",
	"created_at": 1792486800,
	"session": "a41c9e0f",
	"version": "v-7d21",
	"background": true,
	"status": "in_progress",
	"output": [],
	"error": null,
	"incomplete_details": null
}
```

The work goes on after the request ends. Read the result later with `GET /v1/sessions/:sessionId` (the `response` field), the wait route, or `GET /v1/sessions/:sessionId/turns/:turnId`.
The final `status` is `completed`, `incomplete`, `failed` or `cancelled`. Each item in `output` is an assistant message with `output_text` parts. `usage` shows the tokens.

### Stream the answer

With `"stream": true`, OpenBot answers `200` with Server-Sent Events (SSE). SSE is a simple format for a stream of events over HTTP.

```sh
curl -N -H "Authorization: Bearer $OPENBOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"expected":0,"input":"Plan three days in Rome.","stream":true}' \
  https://api.example.com/v1/sessions/$SESSION/turns
```

```sh
event: response.output_text.delta
data: {"type":"response.output_text.delta","session":"a41c9e0f","turn":"t-19aa","step":1,"sequence_number":4,"item_id":"i-02","output_index":0,"content_index":0,"delta":"Day 1: ","logprobs":[]}
```

The events come in this order: `response.created`, `response.in_progress`, `response.output_item.added`, `response.content_part.added`, many `response.output_text.delta`, `response.output_text.done`, `response.content_part.done`, `response.output_item.done`. The last event is one of `response.completed`, `response.incomplete`, `response.failed` or `response.cancelled`.
The stream only watches the Turn. If you close it, the Turn goes on.

### Common errors

| Status | Error                         | When                                            |
| ------ | ----------------------------- | ----------------------------------------------- |
| `400`  | `SessionModelInvalid`         | The model in `overrides` does not exist.        |
| `404`  | `SessionNotFound`             | You have no Session with this ID.               |
| `409`  | `SessionBusy`                 | The Session already has an unfinished Turn.     |
| `409`  | `SessionConflict`             | `expected` is old, or the Turn could not start. |
| `503`  | `SessionExecutionUnavailable` | OpenBot has no model to run the Turn.           |
| `503`  | `SessionStorageUnavailable`   | OpenBot cannot reach its database.              |

A Turn can also stop and wait: for a decision about a capability, or for work that it gave to another Bot. Its status is then `Waiting`. The wait survives a server restart. See [Requests](/docs/requests) and [Delegation](/docs/delegation).

## Read Turns and Items

`GET /v1/sessions/:sessionId/turns` lists Turn records, oldest first. Use `limit` (1 to 100, default 50) and `after` (a Turn ID). The answer is `{ "items": [...], "next": "<turnId>" | null }`. The list also has Turns that a Fork copied from the source Session.

`GET /v1/sessions/:sessionId/turns/:turnId` returns `{ "turn": {...}, "response": {...} }`. The Turn record has `status`, `settings`, `steps`, `usage`, `start` and `end`. `start` is the Version before the Turn. `end` is the Version after it. A Turn that works for another member than the owner of the Session has `author`, the user ID of that member. In a [Channel](/docs/channels), it is the person who wrote the message.

`GET /v1/sessions/:sessionId/turns/:turnId/items` lists the Items of one Turn, with the same `after` and `limit`. Each Item has `id`, `content` and `origin` (`session`, `turn`, `step`).

## Steer, queue and interrupt

**Steer** adds a message to a running Turn. The Bot reads it at its next step.

```sh
curl -H "Authorization: Bearer $OPENBOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"input":"Keep it cheap."}' \
  https://api.example.com/v1/sessions/$SESSION/turns/$TURN/steer
```

OpenBot returns `202` with `session`, `turn`, `item`, `revision` and `version`. If the Turn does not run, you get `409`. A Turn with an `author` takes steer messages only from that author.

**Queue** saves a message for later: `POST /v1/sessions/:sessionId/queue` with `{ "input": ..., "expected"?: <revision> }`. When the current Turn ends, OpenBot starts the next queued message as a new Turn. The answer is `202` with `session`, `item` and `revision`.

**Interrupt** stops a Turn: `POST /v1/sessions/:sessionId/turns/:turnId/interrupt` with the body `{}`. The Turn status becomes `Interrupted` and the response status becomes `cancelled`. A Turn that has already ended returns `409`.

**Resume** cleans up after a restart: `POST /v1/sessions/:sessionId/resume`. If a saved Turn still says it runs but no server runs it (`activity: "historical"`), OpenBot marks it `Interrupted`. It does not run the Turn again. A `Waiting` Turn is not touched, because its wait is saved.

## Todo list

A Session has a todo list. The Bot keeps it with the tool `openbot_todos` when its work has more than one step. Each item has an `id`, a `content` and a `status`: `pending`, `in_progress` or `done`. Only one item can be `in_progress` at a time.

While an item is not `done`, the Bot goes on working. When the Bot wants to end the Turn with open items, OpenBot adds a reminder with the open items, and the Bot takes one more step. OpenBot reminds it only once for each state of the list. So if the Bot stops again and the list did not change, the Turn ends.

Read the list with `GET /v1/sessions/:sessionId/todos`:

```json
{
	"items": [
		{ "id": "read", "content": "Read the open issues", "status": "done" },
		{ "id": "fix", "content": "Fix the login bug", "status": "in_progress" }
	]
}
```

Replace the whole list with `PUT /v1/sessions/:sessionId/todos`. Send the Version and the revision of the Session that you read:

```json
{
	"expected": "<version>",
	"revision": 7,
	"items": [
		{ "id": "fix", "content": "Fix the login bug", "status": "pending" }
	]
}
```

The answer is the Session view. An old Version or revision returns `409` with `SessionConflict`. So does a list where two items have the same `id`, or where more than one item is `in_progress`.

The list is part of the Timeline. A Fork or a restore of an older Version has the list of that Version.

## Wait

A Bot can wait with the tool `openbot_wait`. It gives `seconds`, or `until` with a date and time, such as `2026-10-23T09:00:00Z`. The Turn becomes `Waiting`. When the time comes, the tool call gets `{ "waited": true, "at": "<time>" }`, and the Turn goes on.

OpenBot saves each wait. After a restart, the wait goes on until its time. A wait whose time passed while no server ran goes on right after the start. An interrupt of the Turn ends its waits.

To wait for the work of several Bots at once, the Bot gives them their tasks with several `openbot_delegate` calls in the same step. The Turn goes on when all of them are done. See [Delegation](/docs/delegation).

## Plan mode

In `plan` mode, the Bot looks things up, but it does not change anything yet. It gets only the tools that just read: the Bot tools that list and read Bots, App resources and prompts, and the App tools that the organization lists in `appReadRules`. It also gets the todo tool and the wait tool.

When the plan is ready, the Bot calls `openbot_submit_plan` with the steps as a todo list and a short summary. OpenBot saves the list and makes a [request](/docs/requests) for the capability `plans.run`. The Turn waits.

- When the request is allowed, the Session moves to `build` mode. A new Turn starts with all tools, and the Bot carries out the plan.
- When it is denied, the Bot gets the reason and stays in `plan` mode.

The approval setting says who answers and what happens when nobody answers in time:

```json
{ "approver": "person", "timeoutMs": 600000, "onTimeout": "run" }
```

| Field       | Values             | What it does                                                                                              |
| ----------- | ------------------ | --------------------------------------------------------------------------------------------------------- |
| `approver`  | `chain`, `person`  | `chain` asks the decider above the Bot, so a Grant or a Rule can answer. `person` always asks the person. |
| `timeoutMs` | 1 second to 7 days | How long the request waits.                                                                               |
| `onTimeout` | `run`, `stay`      | `run` carries out the plan when nobody answers in time. `stay` keeps the Session in `plan` mode.          |

You can set it in four places. The most specific one that is set wins, also when it is looser:

1. The Session: `planApproval` when you create it, or with `PATCH /v1/sessions/:sessionId`. Send `null` to remove it.
2. The Bot: `planApproval` on the [Bot](/docs/bots).
3. You: `PATCH /v1/me/settings` with `{ "expectedVersion": 0, "planApproval": { ... } }`. Read your settings with `GET /v1/me/settings`. The same settings hold your [default Bot](/docs/bots#your-default-bot).
4. The organization: `planApproval` in its [settings](/docs/organization#settings). It is only the default. It cannot forbid a looser setting.

## Models and execution mode

`GET /v1/sessions/:sessionId/models` shows the models you can pick:

```json
{
	"selected": {
		"_tag": "Config.Selection",
		"provider": "development",
		"model": "mock-text"
	},
	"providers": [
		{ "id": "development", "name": "Development scenarios (simulated)" }
	],
	"models": [
		{
			"_tag": "Config.Model",
			"provider": "development",
			"id": "mock-text",
			"name": "mock-text (simulated)",
			"reasoningEfforts": [],
			"serviceTiers": []
		}
	]
}
```

Pick a model for the Session with `PUT /v1/sessions/:sessionId/model`:

```json
{
	"expected": 4,
	"selection": {
		"_tag": "Config.Selection",
		"provider": "development",
		"model": "mock-slow"
	}
}
```

A wrong choice returns `400` with `SessionModelInvalid`. The `reason` is `provider-not-found`, `model-not-found` or `unsupported-option`. To use a model for one Turn only, put the selection in `overrides.model` when you start the Turn. See [Models](/docs/models) for how OpenBot gets its models.

The execution mode is `build` or `plan`. `build` is the normal mode: the Bot does the work. In `plan` mode, the Bot writes a plan first. See [Plan mode](#plan-mode). Set the mode with `PUT /v1/sessions/:sessionId/mode` and `{ "expected": 4, "mode": "plan" }`, or with `settings.mode` when you create the Session. OpenBot saves the mode on the Session and copies it into each new Turn's `settings`.

`PUT /v1/sessions/:sessionId/settings` replaces all settings at once: `{ "expected": 4, "settings": { "mode": "build" } }`.

## Fork from a Version

A **Fork** makes a new Session that starts from a Version of another Session. The source Session does not change.

```sh
curl -H "Authorization: Bearer $OPENBOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"version":"v-7d21","title":"Rome, plan B"}' \
  https://api.example.com/v1/sessions/$SESSION/fork
```

All fields are optional: `version`, `title` and `settings`. Without `title`, the Fork keeps the title of its source. Without `version`, the Fork starts from the latest complete point. OpenBot returns `201` with the new Session view. Its `session.forkedFrom` names the source Session and Version.

To find Versions, use `GET /v1/sessions/:sessionId/versions`. To see the history at one Version, use `GET /v1/sessions/:sessionId/history?version=<versionId>`.

### Regenerate an answer

To get a new answer to the same question, fork from the Version before that Turn. Then start a new Turn with the same input.

1. Read the Turn with `GET /v1/sessions/$SESSION/turns/$TURN`. Note `turn.start`. `turn.input` lists the IDs of the input Items. Read their text with the Items route.
2. Fork with `{ "version": "<turn.start>" }`. Note the new `session.id` and `session.revision`.
3. Start a Turn in the new Session with the same `input`.

## Export and import

`GET /v1/sessions/:sessionId/record` exports the whole Session as one record. The record has `formatVersion`, `session`, `versions` and `messages`.

`PUT /v1/sessions/:sessionId/record` imports a record. The body is `{ "record": {...}, "expected": ... }`:

- Use `"expected": null` to make a new Session from the record.
- To replace an existing Session, set `expected` to its current `session` object from `GET /v1/sessions/:sessionId`.

The record's `session.id` must match the path. If it does not, OpenBot returns `400` with `SessionInvalidRecord`. If a Turn runs, OpenBot returns `409` with `SessionBusy`.
An import restores data only. It does not restart a Turn.

See all fields in the [Sessions reference](/docs/api/operations/tags/sessions/).
