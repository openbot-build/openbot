---
title: Alerts
description: Send Platform errors to a Lark chat.
---

Platform can send a short message to a Lark chat when something fails on the server.
Lark is a chat app. A custom bot in a Lark group can receive messages from a URL, called a webhook.

Alerts are off by default. Platform always writes its normal logs, with or without alerts.

---

## Turn on alerts

<Steps>
<Step>

### Make a custom bot

In a Lark group, add a **custom bot**. Copy its webhook URL. It looks like this:

```txt
https://open.larksuite.com/open-apis/bot/v2/hook/0a1b2c3d-4e5f-6789-abcd-ef0123456789
```

If you turn on **signature verification** for the bot, also copy its signing secret.

</Step>
<Step>

### Set the variables

```sh
OPENBOT_LARK_WEBHOOK_URL=https://open.larksuite.com/open-apis/bot/v2/hook/0a1b2c3d-4e5f-6789-abcd-ef0123456789
OPENBOT_LARK_SIGNING_SECRET=your-signing-secret
OPENBOT_ENVIRONMENT=production
OPENBOT_VERSION=1f2e3d4
OPENBOT_INSTANCE=api-1
```

</Step>
<Step>

### Restart Platform

Platform reads the variables when it starts. Both the production program and the development server can send alerts.

</Step>
</Steps>

| Variable                      | Default       | Meaning                                                             |
| ----------------------------- | ------------- | ------------------------------------------------------------------- |
| `OPENBOT_LARK_WEBHOOK_URL`    | empty         | The webhook URL. Empty turns alerts off.                            |
| `OPENBOT_LARK_SIGNING_SECRET` | empty         | The signing secret. Empty sends messages without a signature.       |
| `OPENBOT_ENVIRONMENT`         | `development` | A label for the environment. Production Compose sets `production`.  |
| `OPENBOT_VERSION`             | `unknown`     | A label for the release. Production Compose sets `OPENBOT_RELEASE`. |
| `OPENBOT_INSTANCE`            | host name     | A label for this server. Empty means the host name of the machine.  |

The webhook URL must start with `https://open.larksuite.com/open-apis/bot/v2/hook/`. If it does not, Platform does not start.
The error does not show the URL.

Treat the webhook URL and the signing secret as passwords. Anyone with the URL can post to your group.

When you set a signing secret, each message has a `timestamp` and a `sign` field. The sign is an HMAC-SHA256 value made from the timestamp and the secret, as Lark expects.

---

## What causes an alert

Platform sends an alert for these failures:

| Source    | When                                                               |
| --------- | ------------------------------------------------------------------ |
| `http`    | A request ends with a status of `500` or higher.                   |
| `turn`    | A Turn ends with the status `Failed`.                              |
| `startup` | Platform fails to start, for example because of bad configuration. |

Normal request errors, such as `400`, `401`, `404`, or `409`, do not cause alerts. Work that a person interrupts on purpose does not cause alerts either.

## What a message contains

Each message is plain text. For example:

```txt
Platform Error: Operation failed
environment: production
version: 1f2e3d4
instance: api-1
time: 2026-10-20T08:15:30.120Z
eventId: 6f1c0d2e-8a4b-4c5d-9e6f-0a1b2c3d4e5f
source: http
operation: http.request
errorType: SessionStorageUnavailable
location: ManagedSessions.ts:412:17
requestId: 2b7e9f40-1c3d-4e5f-8a9b-0c1d2e3f4a5b
method: POST
route: /v1/sessions/:sessionId/turns
status: 503
```

| Line                                     | Meaning                                                                  |
| ---------------------------------------- | ------------------------------------------------------------------------ |
| `environment`, `version`, `instance`     | The labels from your variables.                                          |
| `time`, `eventId`                        | When it happened, and a new random ID for this alert.                    |
| `source`, `operation`                    | Which part of Platform failed.                                           |
| `errorType`                              | The name of the error, such as its `_tag`.                               |
| `location`                               | The file name, line, and column in the code. No folder path.             |
| `requestId`, `method`, `route`, `status` | For HTTP failures. `route` is the route pattern, not the real path.      |
| `sessionId`, `turnId`                    | For Turn failures.                                                       |
| `additionalOccurrences`                  | Only in a repeat summary. How many more times the same failure happened. |

Use `eventId`, `requestId`, `sessionId`, and `turnId` to find the matching lines in your server logs.

### What is never sent

To keep data private, an alert never contains:

- the log message or the error message,
- user input, model context, or tool parameters,
- request bodies, query strings, full URLs, or cookies,
- API keys, tokens, or other credentials.

Every value must be a short, safe ID. If a value has other characters, Platform leaves it out or uses `unknown`.

## Limits

Platform sends alerts in the background. A slow or broken Lark bot never slows down your requests.

| Limit           | Value        | What happens                                                                             |
| --------------- | ------------ | ---------------------------------------------------------------------------------------- |
| Queue           | 256          | Messages wait in a queue. When it is full, new messages are dropped.                     |
| Repeat window   | 60 seconds   | The first failure is sent. Repeats of the same failure in the window are counted.        |
| Repeat groups   | 128          | Platform tracks at most 128 different failures at the same time. More are dropped.       |
| Send rate       | 1 per second | Platform waits at least one second between two messages.                                 |
| Request timeout | 2 seconds    | A slow request counts as a failed attempt.                                               |
| Attempts        | 3            | Platform tries again after network errors, timeouts, `429`, `5xx`, and Lark rate limits. |
| Shutdown        | 5 seconds    | On shutdown, Platform tries to send waiting messages for up to five seconds.             |

Two failures are "the same" when they have the same `source`, `operation`, `errorType`, and `location`.
When the window ends and there were repeats, Platform sends one summary with the title `Repeated failure` and `additionalOccurrences`.

When messages are dropped or cannot be sent, Platform writes a warning to its own log. These warnings never cause new alerts.

<Callout type="info">
	Alerts are best effort. A crash can lose waiting messages. A retry can send
	the same message twice. Each server process has its own queue and limits, even
	when they share one bot.
</Callout>

## Alerts in your own program

When you run Platform from your own code, add alerts with `Lark.layer`. It adds a logger and keeps your other loggers. It needs an `HttpClient`.

```ts
import { NodeRuntime } from "@effect/platform-node"
import {
	EnvironmentConfiguration,
	Lark,
	LarkConfiguration,
	Server,
} from "@openbot-build/platform"
import { Effect, Layer, Option } from "effect"
import { FetchHttpClient } from "effect/http"

NodeRuntime.runMain(
	Effect.gen(function* () {
		const lark = Option.match(yield* LarkConfiguration.load, {
			onNone: () => Layer.empty,
			onSome: (settings) =>
				Lark.layer(settings).pipe(Layer.provide(FetchHttpClient.layer)),
		})
		const settings = yield* EnvironmentConfiguration.load
		return yield* Layer.launch(Server.layer(settings)).pipe(
			Effect.provide(lark),
		)
	}),
)
```

`LarkConfiguration.load` reads the variables above. It returns `Option.none()` when the webhook URL is empty.
Add the logger outside the server, as above, so that it stays open until the server has closed.

`Lark.layer` also takes these optional settings: `capacity`, `aggregationCapacity`, `windowMs`, `intervalMs`, `requestTimeoutMs`, and `shutdownTimeoutMs`.

Any log at level `Error` or `Fatal` becomes an alert. To give it good labels, add the annotations `source` and `operation` to your log:

```ts
Effect.logError("Import failed").pipe(
	Effect.annotateLogs({ source: "importer", operation: "import.run" }),
)
```
