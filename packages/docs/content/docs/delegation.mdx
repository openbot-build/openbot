---
title: Delegation
description: How Bots give work to other Bots and get the results back.
---

**Delegation** means that one Bot gives a task to another Bot. The other Bot works in its own Session, with its own context. Only a short brief goes down, and only a short result comes back. So each Bot keeps its attention on its own work.
This page shows the Bot tools, the brief and the result, and how to watch delegated work.

---

## The Bot tools

OpenBot gives every Bot these tools:

| Tool                        | What it does                                                                                   |
| --------------------------- | ---------------------------------------------------------------------------------------------- |
| `openbot_list_bots`         | Lists the Bots it can give work to, with their roles. It includes its Session Bots.            |
| `openbot_bot_details`       | Reads the role and instructions of one Bot.                                                    |
| `openbot_delegate`          | Gives a task to another Bot and waits for the result.                                          |
| `openbot_start_session_bot` | Starts a new [Session Bot](/docs/bots#three-kinds-of-bots) for its Session.                    |
| `openbot_create_bot`        | Makes a new lasting Bot that it owns. See [Bots that own Bots](/docs/bots#bots-that-own-bots). |
| `openbot_promote_bot`       | Makes a Session Bot of its Session a lasting Bot that it owns.                                 |
| `openbot_report`            | Only in delegated work. Sends the result back.                                                 |

The first time a Bot gives work to another lasting Bot, starts a Session Bot, makes a Bot or promotes one, the decider above it must agree. See [Requests](/docs/requests). A Bot can always give work to the Session Bots of its Session and to the Bots that it owns.

---

## The brief

`openbot_delegate` takes a brief:

| Field            | Meaning                                                          |
| ---------------- | ---------------------------------------------------------------- |
| `bot`            | The ID of the other Bot.                                         |
| `reason`         | Why the Bot wants this. A decider reads it when one must agree.  |
| `task`           | What to do.                                                      |
| `userRequest`    | The words of the person, unchanged. A brief never replaces them. |
| `context`        | Short facts that the other Bot needs.                            |
| `references`     | Session and Item IDs that the other Bot can read.                |
| `constraints`    | Rules for the work.                                              |
| `expectedOutput` | What a good result looks like.                                   |
| `session`        | Optional. Continue earlier work of that Bot in this Session.     |

The other Bot gets the brief as the first message of a Turn. It never sees the history of the Bot that gave the work.

### Which Session the work uses

- With `session`, the work goes on in that Session, if it belongs to the other Bot and was started from the same Session.
- For a Session Bot, the work goes on in its latest Session from the same parent Session. So a Session Bot keeps its context.
- Otherwise the work starts in a new Session.

If the other Session is busy, the brief waits in its queue and runs next.

## The result

The other Bot calls `openbot_report` once when it is done. If it ends without a report, OpenBot uses its last answer.

```json
{
	"status": "completed",
	"summary": "Added the endpoint and two tests.",
	"artifacts": [{ "kind": "branch", "ref": "bots-contract" }],
	"openQuestions": [],
	"child": { "session": "c81d…", "turn": "t-77" }
}
```

`status` is `completed`, `failed` or `cancelled`. The result never holds the full history. To read the details, open the Session in `child`.

## How the parent waits

While the other Bot works, the Turn that gave the work has the status `Waiting`. It does not hold a running process, so the wait can last long and survives a server restart. When the work ends, OpenBot gives the result to the waiting tool call, and the Turn goes on. When a Turn gives work to several Bots at once, it goes on after the last result.

Delegated Sessions have `kind: "delegated"` and a `parent` with the Session, Turn and tool call that started them. They have the same routes as every Session. You can read them, steer them and interrupt them.

## Watch delegated work

```sh
curl -H "Authorization: Bearer $OPENBOT_TOKEN" \
  https://api.example.com/v1/sessions/$SESSION/delegations
```

```json
[
	{
		"id": "dlg_9f1e…",
		"parent": { "session": "a41c…", "turn": "t-12", "toolCallId": "call-3" },
		"bot": "bot_5c0e…",
		"child": { "session": "c81d…", "turn": "t-77" },
		"status": "running",
		"brief": { "task": "…", "userRequest": "…" },
		"result": null
	}
]
```

| Status        | Meaning                                                        |
| ------------- | -------------------------------------------------------------- |
| `authorizing` | The work waits for a [request](/docs/requests) to be answered. |
| `queued`      | The work may start. OpenBot starts it now.                     |
| `running`     | The other Bot works on it.                                     |
| `completed`   | The work is done. `result` holds the result.                   |
| `failed`      | The work failed or was not allowed.                            |
| `cancelled`   | The work was stopped.                                          |

## Stop delegated work

When you [interrupt](/docs/sessions#steer-queue-and-interrupt) a Turn, OpenBot also stops the work that it gave away, and closes its open requests. Each record becomes `cancelled`.

## Forks

A Fork of a Session is new direct work. It keeps the Bot of its source, but it has no `parent`. Work that a Fork gives away starts in new Sessions, so two branches never share the work of one Session Bot.
