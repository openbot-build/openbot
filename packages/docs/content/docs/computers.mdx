A Computer is a machine a Bot can use to run commands and work with files. It
can be a provider sandbox or a machine paired by its operator.

## Choose a machine

Use a Computer you may access, or ask for one. Check which files and services
are on it before giving a Bot access. The Computer is the access boundary: a Bot
with access can work throughout that machine.

## Give work

Give the Bot a task and the Computer it should use. Access to a Computer,
creating a sandbox, deleting it, and opening a public port can need
[decisions](/docs/requests). An open public port can be used by anyone with its
address.

The client can show commands, files, and desktop operations when the machine
supports them. An offline paired machine needs its operator to reconnect it.

## End access and check cost

Remove the Bot access when it is no longer needed. Deleting a sandbox also
deletes its files. Save needed results first. Idle sandboxes may pause; your own
paired machine does not. Provider charges are separate from model budgets. A
model budget does not stop a Computer.

Removing access stops further commands and output reads through OpenBot. If an
input or file change has an unknown result, check the machine before trying it
again. A lost connection does not prove that the last action stopped.

Creating, pausing, resuming and deleting a Computer use saved executions. You
can reconnect to their events without starting the action again. A lost provider
reply leaves an unknown result for a person to check. A cancel request alone
does not mean the sandbox has stopped. Automatic idle pauses and resumes follow
the same rules.

## Keep the results

A Bot saves completed deliverables with `openbot_computer_export_file`. It reads
one file from a Computer it may use and saves it in the member's Files. The tool
takes `computer`, `path`, `name` and `mediaType`. Its result has the native
`file` metadata and a `uri` such as `openbot-file:file_…`; it does not put
binary bytes in the model context. Clients can show a download next to the tool
result.

The file stays linked to its Chat when the temporary Computer stops. Normal file
permissions, size, type and member quota limits apply. The administrator must
configure object storage and allow the output type, such as a PowerPoint file.
An export failure is not a saved deliverable. The Bot must keep the source,
explain the failure, and must not delete or release it before export succeeds.

Reconnecting or replaying the same durable tool call returns the same file. A
lost storage reply is checked before another upload. If the source changed after
a pending export started, that export fails instead of replacing its bytes.

An already uploaded file can also be saved to an idle Chat with
`POST /v1/chats/:chatId/files` and `{ fileId, requestId, expected }`. It creates
a user attachment in history, without starting a Turn. Reuse the same request ID
when checking a lost reply. Current or queued work blocks a new attachment. This
saved attachment is a download reference. Future model calls receive an explicit
reference note, not the file bytes. Files submitted as normal message input keep
their existing content behavior.
