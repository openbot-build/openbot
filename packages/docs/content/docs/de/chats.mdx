Ein Chat ist dein Gespräch mit einem Bot. OpenBot behält einen direkten Chat für
dich und jeden Bot. Dein Client zeigt Nachrichten und Arbeit darin.

## Arbeit geben und lenken

Nenne das gewünschte Ergebnis und die nötigen Angaben. Füge bei Bedarf
[Dateien](/de/docs/files) hinzu. Ein Arbeitsabschnitt heißt Turn. Eine weitere
Nachricht desselben Autors kann den laufenden Turn lenken. In einer Gruppe
wartet eine andere Person gegebenenfalls auf ihren eigenen Turn.

Nutze den Planmodus, wenn du zuerst einen Plan möchtest. Prüfe, ob der Plan eine
Freigabe braucht. Eine Aufgabenliste zeigt Schritte, beweist aber keinen
Abschluss. Der Bot kann auch eine Erinnerung setzen, um später zur Aufgabe
zurückzukehren.

## Das Ergebnis lesen

Der Client kann einen Stream oder eine fertige Antwort zeigen. Lange
[Delegationen](/de/docs/delegation), [Anfragen](/de/docs/requests) und
Erinnerungen können später weitere Nachrichten bringen. Prüfe neben der letzten
Antwort auch offene Arbeit. Das Schließen eines Streams stoppt die Arbeit nicht.

Lange Gespräche können für das Model zusammengefasst werden. Gib wichtige
Angaben erneut, wenn der Bot sie braucht.

## Arbeit stoppen oder löschen

Unterbrich einen laufenden Turn im Client, wenn er stoppen soll. Prüfe auch
getrennte Hintergrundarbeit. Das Stoppen nimmt bereits ausgeführte
App-Handlungen nicht zurück.

Das Löschen des Verlaufs entfernt den Chat-Verlauf, aber nicht das
[Bot-Gedächtnis](/de/docs/memory). Dateien, die nur dieser Chat hält, können
später verschwinden. Lies bei einem fehlgeschlagenen Turn den Fehler, bevor du
dieselbe Aufgabe erneut sendest.

## Eigene Gespräche und gespeicherte Befehle

Mit `POST /v1/chats`, `botId` und einer festen `requestId` entsteht eine eigene
`conversation` mit einem vorhandenen Bot. Sein direct Chat bleibt getrennt.
`POST /v1/chats/:chatId/forks` kopiert den gespeicherten Verlauf der angegebenen
Revision, ohne Nachrichten oder Werkzeuge erneut auszuführen. Offene Arbeit,
Freigaben und unklare externe Ergebnisse verhindern eine Kopie.
`GET /v1/chats/:chatId/branches` zeigt nur lesbare Zweige.

`memory: { read, write }` bei einer Chat-Änderung legt die Vorgabe fest.
Dasselbe Feld einer Nachricht gilt nur für diesen Turn. Eine neue Vorgabe
widerruft wartende Speicherarbeit. Kopierter Verlauf wird nicht erneut gelernt.

Bei einer verlorenen Antwort liest `GET /v1/execution-commands/:commandKey` den
Beleg oder `null` mit den aktuellen Konto- und Ausführungsrechten. `null`
beweist nicht, dass der Befehl nie gesendet wurde. Prüfen Sie den alten Befehl
weiter, ohne eine neue Nachricht zu senden. Die native Execution-API liefert
Zustand und Ereignisse.

## Standardmodell der Organisation

Administratoren können `chatModel` mit `PATCH /v1/organization/settings` und der
aktuellen `expectedVersion` setzen. Das Modell muss ein verfügbares Sprachmodell
sein, das der Administrator verwenden darf. Eine explizite Chat-Auswahl hat
Vorrang vor dem Bot-Modell; danach folgt der Organisationsstandard. Neue Chats
behalten diese Vererbung. Jeder Turn speichert seine aufgelöste Auswahl vor dem
externen Aufruf. Änderungen gelten deshalb für folgende Turns, nicht für die
Wiederherstellung bereits angenommener Arbeit. Vorhandene explizite Auswahlen
bleiben erhalten. `model: null` mit der aktuellen Bot-Revision stellt die
Vererbung wieder her.

Nachrichtenquittungen können `inputItems` mit den ursprünglichen Inbox-IDs
dieses Befehls enthalten. Ein `InputMoved`-Ereignis gehört nur dann zu dieser
Nachricht, wenn seine `items` diese IDs enthalten. Fehlen die IDs in einer
älteren Quittung, darf der Client die Zuordnung nicht erraten. Arbeit ohne Turn
liefert `turn: null`; eine Chat-ID ist keine Turn-ID.
