Für Entwickler, die einen Client mit OpenBot verbinden oder den Server
erweitern. Die Beispiele brauchen die auf dieser Seite genannten Rechte. Beginne
mit dem [Entwicklerhandbuch](/de/developers).

Für Mitwirkende, die OpenBot ändern oder veröffentlichen.

## GitHub Actions

Der Workflow `.github/workflows/ci.yml` läuft für Pull Requests, Pushes auf
`main` und Tags wie `v1.2.3` oder `v1.2.3-beta.0`. Die anderen Jobs laufen nur,
wenn `check` erfolgreich ist.

| Job               | Wann            | Was er tut                                                                                                                              |
| ----------------- | --------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `check`           | Immer           | Führt `pnpm build`, `pnpm typecheck`, `pnpm -r test` und `pnpm test:packages` in `devenv shell` aus und packt alle öffentlichen Pakete. |
| `github-packages` | Pushes und Tags | Veröffentlicht die gepackten Pakete in GitHub Packages.                                                                                 |
| `npm`             | Tags            | Veröffentlicht die gepackten Pakete mit Trusted Publishing auf npm.                                                                     |
| `images`          | Immer           | Baut, prüft, scannt und veröffentlicht die Docker-Images.                                                                               |

Alle Jobs laufen auf `ubuntu-latest`. Sie installieren Nix mit dem Determinate
Nix Installer und danach devenv 2.4.0.
[Magic Nix Cache](https://github.com/DeterminateSystems/magic-nix-cache-action)
speichert Nix-Build-Ergebnisse im Cache von GitHub Actions. So bauen spätere
Läufe sie nicht noch einmal. Die Jobs laden auch fertig gebaute devenv-Pakete
von `devenv.cachix.org`. Der Job `check` speichert den pnpm-Store in einem
Cache.

Der Job `images` macht diese Schritte:

1. [hadolint](https://github.com/hadolint/hadolint) und
   `docker buildx bake lint` prüfen das `Dockerfile`. Der zweite führt die
   [Docker-Build-Prüfungen](https://docs.docker.com/build/checks/) aus.
2. Docker Bake baut beide Images. Die Build-Schichten bleiben im Cache von
   GitHub Actions, mit einem Cache pro Image. So bauen spätere Läufe nur, was
   sich geändert hat.
3. `deploy/docker/check.sh` prüft die Images. Siehe
   [Die Images prüfen](#die-images-prüfen).
4. [dive](https://github.com/wagoodman/dive) prüft, dass die Image-Schichten
   keinen Platz verschwenden.
5. [Trivy](https://trivy.dev) scannt beide Images. Der Job schlägt fehl, wenn
   ein Image eine bekannte Schwachstelle der Stufe `HIGH` oder `CRITICAL` hat,
   für die es eine Korrektur gibt. Trivy sieht die Node.js-Version nicht, denn
   Node.js wird in das Image kopiert und nicht als Paket installiert.
6. Der Job speichert beide Images als Artefakt `images-<commit-sha>` für sieben
   Tage.
7. Bei Pushes veröffentlicht der Job die Images. Er nutzt den Build-Cache und
   baut also nicht noch einmal.

Der Workflow läuft für Pull Requests, Pushes auf `main` und Tags wie `v1.2.3`.
Er veröffentlicht Images nur bei Pushes:

| Ereignis             | Veröffentlichte Tags        |
| -------------------- | --------------------------- |
| Ein Push auf `main`  | `<commit-sha>` und `latest` |
| Ein Tag wie `v1.2.3` | `<commit-sha>` und `v1.2.3` |

Die Images landen in der GitHub Container Registry, unter
`ghcr.io/openbot-build/openbot` und
`ghcr.io/openbot-build/openbot/protocol-test`. Der Workflow bringt OpenBot nicht
in Betrieb. Wenn du ein veröffentlichtes Image mit Compose nutzen willst, lade
es herunter und gib ihm den Tag `openbot:<tag>`.

### Pakete veröffentlichen

Alle öffentlichen Pakete erscheinen zusammen mit einer Version.
`pnpm packages:pack` setzt diese Version in jedem öffentlichen Paket, legt die
Abhängigkeiten zwischen ihnen auf diese Version fest, packt sie nach `.release/`
und hält den Hash jeder Datei in `.release/release.json` fest. Die Jobs zum
Veröffentlichen veröffentlichen genau diese Dateien und bauen nicht noch einmal.

| Ereignis                    | Version                             | npm-Tag                    | Veröffentlicht in       |
| --------------------------- | ----------------------------------- | -------------------------- | ----------------------- |
| Ein Push auf `main`         | `0.0.0-commit-<vollständiger Hash>` | `sha-<vollständiger Hash>` | GitHub Packages         |
| Ein Tag wie `v1.2.3-beta.0` | `1.2.3-beta.0`                      | `alpha`, `beta` oder `rc`  | GitHub Packages und npm |
| Ein Tag wie `v1.2.3`        | `1.2.3`                             | `latest`                   | GitHub Packages und npm |

Ein Vorab-Tag nennt seinen Kanal, `alpha`, `beta` oder `rc`, gefolgt von einer
Zahl. Seine Pakete werden nie `latest`. Kein Tag geht auf eine ältere Version
zurück: Eine ältere Version, die später hochgeladen wird, erscheint unter
`backport`, bei Vorabversionen unter `alpha-backport`, `beta-backport` oder
`rc-backport`.

Jede Registry hat eine eigene Concurrency-Gruppe, `publish-github-packages` oder
`publish-npm`, mit `queue: max`. So veröffentlichen zwei Läufe nie gleichzeitig
in dieselbe Registry. Ein erneuter Lauf überspringt eine Version, die es mit
demselben Inhalt schon gibt, und bricht ab, wenn der Inhalt abweicht. Bevor du
von Hand veröffentlichst, warte, bis die wartenden Jobs für diese Registry
fertig sind.

Die `.npmrc` des Repositorys leitet den Scope `@openbot-build` zu GitHub
Packages. Das Release-Skript setzt auch die Registry des Scopes, daher
veröffentlicht es immer in der Registry, die du angibst.

So veröffentlichst du eine Version:

1. Stelle sicher, dass `main` die CI besteht.
2. Setze einen Tag auf den Commit und pushe ihn, etwa `v1.2.3` für ein stabiles
   Release oder `v1.2.3-beta.0` für eine Vorabversion:

   ```sh
   git tag v1.2.3
   git push origin v1.2.3
   ```

3. Der Job `npm` wartet auf die Umgebung `npm`, falls sie eine Freigabe
   verlangt, und veröffentlicht dann.

Der Job `npm` nutzt
[Trusted Publishing](https://docs.npmjs.com/trusted-publishers) von npm: npm
akzeptiert das OIDC-Token des Workflow-Laufs statt eines Zugriffstokens und fügt
jedem Paket eine Provenance-Angabe hinzu. Im Repository liegt kein Geheimnis.
Jedes Paket vertraut dem Workflow `ci.yml` von `openbot-build/openbot` in der
Umgebung `npm`:

```sh
npm trust github @openbot-build/client --file ci.yml --repo openbot-build/openbot --env npm --allow-publish
npm trust list @openbot-build/client
```

npm kann nur einem Paket vertrauen, das es schon gibt. Ein neues Paket
veröffentlicht daher zuerst eine Maintainerin oder ein Maintainer einmal aus den
Dateien, die die CI gepackt hat, und richtet das Vertrauen danach ein:

```sh
gh run download <run id> --name packages-<commit hash> --dir .release
npm login
devenv shell -- pnpm packages:publish npm
```

### Eine Client-Momentaufnahme veröffentlichen

Der Workflow `.github/workflows/sdk-snapshot.yml` läuft bei Pushes auf
`codex/artifact-citation-contract`. Er baut den Client und seine nötigen Pakete,
prüft die API und den Client und packt nur `@openbot-build/client`. Nach diesen
Prüfungen nutzt ein zweiter Job den `GITHUB_TOKEN` des Repositorys. Er
veröffentlicht die Momentaufnahme als `0.0.0-commit-<voller-Hash>` mit dem Tag
`sha-<voller-Hash>`. Der Tag `latest` und die Server-Veröffentlichung bleiben im
Hauptablauf der Veröffentlichung. Der Job zum Veröffentlichen wartet in
derselben Warteschlange `publish-github-packages` wie der Haupt-Workflow.

### Die Doku-Seite veröffentlichen

Der Workflow `.github/workflows/docs.yml` veröffentlicht die Doku-Seite auf
[GitHub Pages](https://docs.github.com/pages) unter
[docs.openbot.build](https://docs.openbot.build). Er läuft bei jedem Push auf
`main`. Du kannst ihn auch von Hand im Tab „Actions“ starten.

| Job      | Was er tut                                                                                                                     |
| -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `build`  | Führt `pnpm --filter "@openbot-build/docs..." build` in `devenv shell` aus. Das baut die Doku und die Pakete, die sie braucht. |
| `deploy` | Schickt `packages/docs/dist` an GitHub Pages.                                                                                  |

Der Job `build` setzt `DOCS_URL` auf `https://docs.openbot.build`. Astro nutzt
den Wert für vollständige Seitenlinks, zum Beispiel in der Sitemap. Es läuft
immer nur ein Deploy auf einmal.

Die Einstellungen des Repositorys müssen **GitHub Actions** als Quelle für Pages
nutzen, mit `docs.openbot.build` als eigener Domain. Setze ihren DNS-CNAME auf
`openbot-build.github.io`. Dieser Actions-Workflow nutzt keine `CNAME`-Datei im
Quellcode. Das englische Handbuch beginnt unter `/`, das chinesische unter
`/zh-cn/` und das deutsche unter `/de/`. Die erzeugte API-Referenz beginnt unter
`/api/`. Siehe
[Manage a custom domain](https://docs.github.com/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site).

### Die Images prüfen

`deploy/docker/check.sh` startet `compose.production.yaml` mit
Test-Einstellungen. Die zusätzliche Datei `compose.check.yaml` entfernt die
Host-Ports und fügt einen zweiten OpenBot-Knoten sowie Einrichtung und Prüfungen
hinzu. Beide Knoten teilen Datenbank und Geheimnisse. Jeder hat einen eigenen
privaten Host. `setup` läuft nach `migrate`, bevor die Knoten starten. Der
Dienst `check` führt die Prüfungen aus. `check.env` enthält die
Test-Einstellungen. Keine davon ist ein echtes Geheimnis.

Der Dienst `check` führt `check.mjs` im Compose-Netzwerk aus, sobald beide
OpenBot-Knoten und der Protokolltest-Dienst gesund sind. Er prüft, dass:

- `/v1/chats` ohne Schlüssel und mit falschem Schlüssel `401` zurückgibt,
- `/openapi.json` auf beiden Knoten funktioniert,
- private RPC-Aufrufe ohne oder mit falschem Geheimnis scheitern,
- jeder Knoten den anderen mit dem gemeinsamen Geheimnis erreichen kann,
- der Catalog des Protokolltests den richtigen öffentlichen Origin hat,
- die MCP-Erkennung auf dem Protokolltest-Dienst funktioniert.

Beide Knoten binden `check.plugins.yml` nur zum Lesen als ihre Plugin-Datei ein.
Sie schaltet `triggers` aus. Das Skript prüft, dass die Routen von triggers auf
beiden Knoten mit `503` und `FeatureUnavailable` antworten, dass das
OpenAPI-Dokument sie noch hat und dass ein Schreiben in die Datei mit `EROFS`
scheitert. Es startet `openbot-inspect plugins` und prüft, dass beide Knoten
denselben Manifest-Hash in `openbot_execution_runners` geschrieben und keine
Warnung über andere Plugins gegeben haben.

Das Skript prüft auch eine leere Datenbank, eine wiederholte Migration, beide
Runner-Adressen und die Sperre gegen Migration bei laufenden Servern. Jeder Lauf
nutzt ein eigenes Compose-Projekt und entfernt es mit der Test-Datenbank am
Ende. Die Pakettests prüfen Wiederaufnahme und Knotenausfall. Die Image-Prüfung
prüft die Verbindungen und den Start im Produktivaufbau.

Führe dieselben Prüfungen auf deinem Computer aus:

```sh
devenv shell -- pnpm images
devenv shell -- pnpm images:check
devenv shell -- hadolint deploy/docker/Dockerfile
devenv shell -- dive --ci --source docker openbot:local
devenv shell -- trivy image --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed openbot:local
```
