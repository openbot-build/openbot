This page maps the [execution design](/architecture) to source tests and release
checks. The source review date is 2026-10-28. A test listed here is **source
evidence, not a passing test result**. Record the revision, command, result, and
log for each release run. See [end-to-end checks](/developers/testing) for
commands and test service limits.

## Reading the map

The change starts from a recorded baseline of 581 tests. A larger test count
does not prove that every old behavior remains. Tests now live in both source
packages and `packages/e2e`. Keep the old assertion, its new location, or the
approved behavior change when a test moves or goes away.

`packages/e2e/scenarios.json` is the detailed map of user assertions. It has 22
task groups and names normal, edge, and extreme cases. An empty case list makes
no coverage claim. This page adds the shared execution and data move checks.

The tables use these path prefixes:

- `E/` means `packages/e2e/test/`.
- `S/` means `packages/server-testing/test/`.
- Other paths start at the project root.

Tests may use a real database with a fixed model, a real HTTP server with a test
workflow, or a complete server. These are different test scopes. A service Layer
restart is not a process crash. Two service objects in one process are not two
server processes.

## Baseline trace

`packages/e2e/baseline.json` gives one row for each baseline test declaration at
revision `2a123ffae6f5aea2cfa02f36975efbacc83f1305`. It compares 566
declarations in 142 files with the current source. The recorded 581 cases are a
run count; loops and parameterized tests can expand one declaration into several
cases. These counts must not be treated as the same thing.

The source snapshot has 371 unchanged test callbacks and 46 more tests that keep
all their direct assertion syntax. Another 59 same-title tests have changed
assertions; 90 tests need a renamed or replacement case. The trace keeps removed
assertion text, current test titles, and review notes. Matching syntax does not
prove that a shared fixture stayed the same or that a test passed. Recheck this
snapshot after later code changes.

Some changes follow the approved design: a Turn owns its resources; commands
return execution receipts; private causes are sealed; permission lists filter
resources; and failed audit writes roll back decisions. Computer resume is an
explicit saved action. Memory cannot widen an observation without source proof.
A request that expires while a decision waits for its lock grants nothing. These
are recorded changes, not identical old behavior.

`S/MemoryModels.test.ts` checks the spent-budget reply with zero model sends,
released permits, a sealed cause, and a successful call after the budget is
removed. `S/TokenThrottle.test.ts` checks the exact joined text of 40 distinct
parts. `S/ToolCommands.test.ts` keeps both delegation clock cases: an early wake
keeps the saved deadline; takeover after that deadline pauses without another
wait.

B463 maps to the three `S/ExecutionStore.test.ts` cases for sealed data, JSON,
and identity damage. They check storage failure, repair, and a separate missing
record. B202 maps to `E/chat/ExecutionResources.test.ts`: failed tool
construction closes its scope, keeps a saved error ID, and lets the next Turn
succeed. B241 maps to `E/chat/ChatRecovery.test.ts`: a damaged Chat does not
stop another Chat from recovering or taking new input.

The App, Channel, Computer, Live, Code Mode, and Vault mappings check saved
receipts and cleanup children, safe error categories and IDs, and owner checks.
`additionalCurrentChecks` records the newer Pairing and Workflow API cases apart
from the 566 baseline declarations. Pairing waits for the saved deletion result.
Cookie and token callers compare complete records after the request enters its
waiting state. Each mapped case links to its passing local run in
`validationRuns`; those runs have distinct scopes.

Read the fault checks with these scope rules:

- **A01 — Complete server failover:** `S/FullServerCluster.test.ts` covers two
  complete server assemblies. The built release entry and its deployment checks
  are separate evidence. Keep the `full-server-failover` entry in the E2E map
  linked to the source process checks.
- **A02 — Business checkpoints:** the complete-server case cuts PostgreSQL
  connections at a Chat checkpoint and checks one saved model result, Turn, and
  event set after recovery. `S/InputCommands.test.ts` checks rollback and input
  admission. `E/chat/ChatRecovery.test.ts` checks new input after recovery.
- **A03 — Physical owners and shared limits:** resource and permit tests use
  separate service processes. They cover network loss, lost close replies, and
  late release from the old owner. Unknown interactive outcomes stay unknown;
  audio is not replayed. A client disconnect does not prove a provider stopped.
- **A04 — Old data:** `S/MigrationRehearsal.test.ts` starts with the baseline
  schema and saved records. It checks conversion, repeat runs, interrupted
  batches, current reads, and new Chat input. A new database alone does not
  cover this scope.
- **A05 — Revision evidence:** record the source revision and each run's scope.
  Keep optional or skipped checks visible. Compare changed and removed baseline
  assertions before accepting a test-count change.

`scripts/effect-rules.ts` checks `domain-boundary`, `storage-contract-boundary`,
`standalone-boundary`, `execution-boundary`, and `public-entry`.
`pnpm typecheck` runs these rules. They check imports; they do not by themselves
detect every second execution engine or recovery loop. Review new workers,
timers, locks, and RPC handlers against the shared design.

Four more rules guard the plugin host. `graft-boundary` lets only the plugin kit
(the `server-plugin` package), the `src/index.ts` file of each plugin package,
the host (`packages/openbot/src`), the development server, and the tests of the
host, the plugin kit, the development server, and `server-testing` import graft.
It also asks for the name `GraftPlugin` for the `Plugin` of graft.
`feature-lookup` does not let the code or the tests of a server package look for
a feature with `Effect.serviceOption` or `Plugin.optional`. Code lists the
services that it needs instead. `kernel-provide` does not let a plugin publish a
service of the kernel. A plugin publishes only keys of a contract package (a
`*-contract` package), of `api`, `domain`, or `protocol`, or of its own package.
Two keys in kernel packages are open to plugins: `Wallets` in `server-billing`
and `ImportedRecords` in `server-execution`. A test of the preset also checks
that no plugin publishes a key of the kernel. `host-only` lets only the host,
the HTTP files of `server-kernel`, and `server-execution` serve HTTP with
`HttpRouter.serve` or `HttpRouter.toWebHandler`, build the HTTP API with
`HttpApiBuilder.layer`, add a global HTTP middleware, or make a layer from a
workflow. A plugin mounts its routes with `HttpHost` and gives its workflows
with `Workflows.contribute`.

`package-layer` keeps the packages in layers. `core`, `domain`, `protocol`, and
`api` are the base. Over the base, from low to high: `server-database`,
`server-kernel`, `identity-contract`, `server-billing`, `server-execution`,
`tools-contract`, `models-contract`, `apps-contract`, `conversation-contract`,
`model-providers`, `server-plugin`, then the plugin packages (`plugin-<id>`),
then `server-upgrade`, then the host (`openbot`), then `server-development`,
then `server-testing`. A package may import only lower layers. A base package
imports no server package, and `server-database` uses only `core` and `domain`.
`domain-boundary` and `standalone-boundary` check the base packages among
themselves. `public-entry` lets other packages use a server package or the host
only through a key of `exports` in its `package.json`. This is true for tests
too.

Two rules keep the plugins apart. `plugin-boundary` does not let a plugin import
another plugin. This is true for plugin packages and their tests. The host
connects the plugins through graft. `plugin-entry` checks that the
`src/index.ts` file of a plugin package has one export only: the plugin, as the
default export. The entries test of each plugin package checks that its
`package.json` names no other plugin package. Another module of a plugin package
has a key in `exports` only when a program of the host, the development server
(`server-development`), or the test helpers and host tests (`server-testing`)
need it, when the data move (`server-upgrade`) needs it, or when the public
types of the host name it. Review checks this. A worker file is an entry of the
build of its package, but not a key of `exports`, because it starts work when it
loads. The Code Mode worker of `plugin-code` is such a file.

## Data move checks

The [deployment guide](/deploy) gives the maintenance order and secret-key
settings. `packages/server-upgrade/test/DataUpgrade.test.ts` checks an empty
database, exclusion between maintenance and a live server, batch
rollback/resume, and imported history that starts no outside work. These are
foundation checks.

`S/MigrationRehearsal.test.ts` starts from the old schema and records. It works
with the domain conversion tests to check the following before the startup gate
opens:

| Saved data                                                                         | Required checks                                                                                                                                                                  |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Chat, Turn, queued input, tools, approvals, delegation, and Code Mode              | Keep IDs, history, order, owners, limits, and decisions. Link pending work to executions. Missing caller evidence must not create new authority.                                 |
| Apps, OAuth, developer tests, index work, Channels, triggers, and reminders        | Keep connection/proof IDs, encrypted grants and flows, original caller evidence, timers, pending notices, and send outcomes. Unknown old writes remain unknown.                  |
| Files, Vaults, models, organizations, accounts, SSO, and physical resource records | Check object references, foreign keys, owner links, saved secret decoding, and supported connection states. Do not silently drop damaged records.                                |
| Usage, prices, credits, and budgets                                                | Keep confirmed charges and call identity. Keep estimates apart from unknown usage. Re-running conversion must not create another charge.                                         |
| Conversion progress and release gate                                               | Stop midway and resume; repeat the full move; reject a damaged or wrongly encrypted record; check counts and references; block server startup until every required phase passes. |

Keep the backup and object-reference list for the rehearsal. Restoration is
allowed before outside work resumes. After that point, test forward repair so an
old backup cannot cause a second outside write.

The baseline trace links each case to a recorded local run. Its evidence
includes a complete build, type checks and rules over 956 files, and the
standard OpenBot package run with 131 files and 883 tests. That package run
includes the Activity process cases, full-server cluster checks, and migration
rehearsal.

E2E evidence combines the full-suite run with affected-case checks: 31 affected
cases passed in one run, and the DevelopmentApps case passed in a separate
standard-package run. These 32 cases overlap with the full-suite output, so the
counts must not be added. One optional live Cloudflare case was skipped. The
trace records each command, scope, and log; it does not claim one complete final
combined run.

Use CI for the exact release commit to judge release checks, including images,
Compose, scans, and docs. Local test evidence does not replace those jobs.
