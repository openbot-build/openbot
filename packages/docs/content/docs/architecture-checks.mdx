This page maps the [execution design](/architecture) to source tests and release
checks. The source review date is 2026-10-28. A test listed here is **source
evidence, not a passing test result**. Record the revision, command, result, and
log for each release run. See [end-to-end checks](/developers/testing) for
commands and test service limits.

## Reading the map

Tests live in the source packages and in `packages/e2e`. A larger test count
does not prove that every behavior stays. When a test moves or goes away, keep
its assertion in the new place, or write down the approved behavior change.

`packages/e2e/scenarios.json` is the detailed map of user assertions. It has 22
task groups and names normal, edge, and extreme cases. An empty case list makes
no coverage claim. This page adds the shared execution checks.

The tables use these path prefixes:

- `E/` means `packages/e2e/test/`.
- `S/` means `packages/server-testing/test/`.
- Other paths start at the project root.

Tests may use a real database with a fixed model, a real HTTP server with a test
workflow, or a complete server. These are different test scopes. A service Layer
restart is not a process crash. Two service objects in one process are not two
server processes.

## Failure and recovery coverage

These are source checks to run against the final revision. The named case gives
a place to inspect the assertions, not only a filename to count.

| --- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F01 | A second node takes over saved work; member and service work obey the same rule. | `S/ExecutionCluster.test.ts`: `another process takes over ${kind} work from a saved step`; two OS processes, PostgreSQL, owner kill, decisions, cancellation, and late results. `S/TurnCluster.test.ts` checks a saved model result. `S/FullServerCluster.test.ts` starts two complete server assemblies with fixed model/tool adapters and tests public token/cookie commands, observation, approval, cancellation, owner kill, and database loss at a Chat checkpoint. Read the fault checks with these scope rules:

- **A01 — Complete server failover:** `S/FullServerCluster.test.ts` covers two
  complete server assemblies. The built release entry and its deployment checks
  are separate evidence. Keep the `full-server-failover` entry in the E2E map
  linked to the source process checks.
- **A02 — Business checkpoints:** the complete-server case cuts PostgreSQL
  connections at a Chat checkpoint and checks one saved model result, Turn, and
  event set after recovery. `S/InputCommands.test.ts` checks rollback and input
  admission. `E/chat/ChatRecovery.test.ts` checks new input after recovery.
- **A03 — Physical owners and shared limits:** resource and permit tests use
  separate service processes. They cover network loss, lost close replies, and
  late release from the old owner. Unknown interactive outcomes stay unknown;
  audio is not replayed. A client disconnect does not prove a provider stopped.
- **A04 — New database only:** `S/RemoveOldDataMigration.test.ts` checks that
  the migration of this version passes on an empty database and on data of this
  version. It also checks that the migration stops, and changes nothing, on each
  marker of data in a form that this version does not read.
- **A05 — Revision evidence:** record the source revision and each run's scope.
  Keep optional or skipped checks visible. Compare changed and removed
  assertions before accepting a test-count change.

`scripts/effect-rules.ts` checks `domain-boundary`, `storage-contract-boundary`,
`standalone-boundary`, `execution-boundary`, and `public-entry`.
`pnpm typecheck` runs these rules. They check imports; they do not by themselves
detect every second execution engine or recovery loop. Review new workers,
timers, locks, and RPC handlers against the shared design.
`storage-contract-boundary` and `execution-boundary` judge only `src`. A test
calls the HTTP contract as a client does. It may also start a cluster or a local
Chat runtime to make the setting that it checks. That is not server work. The
helpers in `packages/server-testing/src` are test code too, so the rules judge
them as tests.

Four more rules guard the plugin host. `graft-boundary` lets only the plugin kit
(the `server-plugin` package), the `src/index.ts` file of each plugin package,
the host (`packages/openbot/src`), the tests of the host and the plugin kit, and
the helpers and tests of `server-testing` import graft. The development server
uses `Host.layer`, so it does not import graft. It also asks for the name
`GraftPlugin` for the `Plugin` of graft. `feature-lookup` does not let the code
or the tests of a server package look for a feature with `Effect.serviceOption`
or `Plugin.optional`. Code lists the services that it needs instead.
`kernel-provide` does not let a plugin publish a service of the kernel. A plugin
publishes only keys of a contract package (a `*-contract` package), of `api`,
`domain`, or `protocol`, or of its own package. The host publishes `Wallets`
from its own package. A test of the preset also checks that no plugin publishes
a key of the kernel. `host-only` lets only the host, the HTTP files of
`server-kernel`, and `server-execution` serve HTTP with `HttpRouter.serve` or
`HttpRouter.toWebHandler`, build the HTTP API with `HttpApiBuilder.layer`, add a
global HTTP middleware, or make a layer from a workflow. A plugin mounts its
routes with `HttpHost` and gives its workflows with `Workflows.contribute`.

`package-layer` keeps the packages in layers. The name of a package says its
kind, so the rules need no list of packages: `server-*`, `*-contract`,
`model-providers`, and `plugin-*` are server packages, and `plugin-*` are
plugins. `core`, `domain`, `protocol`, and `api` are the base. Over the base,
from low to high: `server-database`, `server-kernel`, `server-billing`,
`server-execution`, `identity-contract`, `tools-contract`, `models-contract`,
`apps-contract`, `conversation-contract`, `model-providers`, `server-plugin`,
then the plugin packages (`plugin-<id>`), then the host (`openbot`), then
`server-development`, then `server-testing`. A package may import only lower
layers. A base package imports no server package, and `server-database` uses
only `core` and `domain`. `domain-boundary` and `standalone-boundary` check the
base packages among themselves. `public-entry` lets other packages use a server
package or the host only through a key of `exports` in its `package.json`. This
is true for tests too.

Two rules keep the plugins apart. `plugin-boundary` does not let a plugin import
another plugin. This is true for plugin packages and their tests. The host
connects the plugins through graft. `plugin-entry` checks that the
`src/index.ts` file of a plugin package has one export only: the plugin, as the
default export. The entries test of each plugin package checks that its
`package.json` names no other plugin package. A worker file is an entry of the
build of its package, but not a key of `exports`, because it starts work when it
loads. The Code Mode worker of `plugin-code` is such a file.

Four rules keep names and paths simple. Each one gives the expected value in its
message, so a fix is a copy.

- `identity-key`: the key of a service, a reference, a middleware, or a symbol
  is `@openbot-build/<package>/<module path>`, plus `/<Name>` when the name of
  the class or `const` is not the name of the module. A test module uses the
  same rule with `test/` in its path. A brand is
  `@openbot-build/<package>/<Name>`. The text that turns the `deterministicKeys`
  check off is a finding too, and `tsconfig.base.json` sets that check of the
  Effect language service to `error`. So the language service and the rules ask
  for the same key.
- `package-layout`: a package keeps its modules flat in `src`. Only a contract
  package of several plugins has folders, one folder for each plugin, named by
  its plugin id. Each key of `exports` points to `dist/<path>.js`, built from
  `src/<path>.ts`, so the import path, the file, and the key of a module agree.
- `no-reexport`: a module does not export a symbol of another workspace package
  again, and it gives no second name to a symbol. A second name is an exported
  constant or type whose whole value is an imported name, such as `X.member`.
  This is true for an import from another module of the same package too. The
  bundle entries of `packages/client` are the only modules that export the code
  of other packages.
- `unused-entry`: a server package or the host has a key in `exports` only when
  another package imports it, or a code sample on a docs page shows it. The `.`
  key of a plugin stays, because the host loads the plugin by its name. An
  import from the same package, its tests too, does not count. A test imports a
  module of its own package that has no key by its source path.

## Release evidence

Run the [project checks](/developers/testing) on one fixed revision. Finish
builds before tests start, because tests and child processes load built files.

| Check                     | Entry point                                                                     | Evidence needed                                                                                                                       |
| ------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Build and types           | `devenv shell -- pnpm build`; `devenv shell -- pnpm typecheck`                  | All packages, test types through package test scripts, and dependency rules.                                                          |
| Package and user tasks    | `devenv shell -- pnpm -r test`                                                  | Full test output, skipped cases, and the final E2E assertion map.                                                                     |
| Fault and migration cases | F01–F11 and A01–A04 above                                                       | Process boundaries, fault point, final state, external effect count, and saved event/call evidence.                                   |
| Images and Compose        | `.github/workflows/ci.yml`, `deploy/docker/check.sh`                            | Docker build checks, Compose startup/migration/API checks, image-layer checks, and vulnerability scan output for the built image IDs. |
| Docs                      | Docs package build and `E/read-docs/Docs.test.ts`; `.github/workflows/docs.yml` | English, Chinese, German, generated API reference, and link checks.                                                                   |
| Merge and push            | CI for the exact merged revision                                                | Required jobs pass. A local focused test or an earlier snapshot is not final CI evidence.                                             |

Use CI for the exact release commit to judge release checks, including images,
Compose, scans, and docs. Local test evidence does not replace those jobs.
