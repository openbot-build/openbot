## GitHub Actions

The workflow `.github/workflows/ci.yml` runs for pull requests, pushes to
`main`, and tags like `v1.2.3` or `v1.2.3-beta.0`. The other jobs run only when
`check` passes.

| Job               | When            | What it does                                                                                                                     |
| ----------------- | --------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `check`           | Always          | Runs `pnpm build`, `pnpm typecheck`, `pnpm -r test`, and `pnpm test:packages` in `devenv shell`, and packs every public package. |
| `github-packages` | Pushes and tags | Publishes the packed packages to GitHub Packages.                                                                                |
| `npm`             | Tags            | Publishes the packed packages to npm with trusted publishing.                                                                    |
| `images`          | Always          | Builds, checks, scans, and publishes the Docker images.                                                                          |

All jobs run on `ubuntu-latest`. They install Nix with the Determinate Nix
installer, and then devenv 2.4.0.
[Magic Nix Cache](https://github.com/DeterminateSystems/magic-nix-cache-action)
keeps Nix build results in the GitHub Actions cache, so later runs do not build
them again. The jobs also download prebuilt devenv packages from
`devenv.cachix.org`. The `check` job keeps the pnpm store in a cache.

The `images` job does these steps:

1. [hadolint](https://github.com/hadolint/hadolint) and
   `docker buildx bake lint` check the `Dockerfile`. The second one runs the
   [Docker build checks](https://docs.docker.com/build/checks/).
2. Docker Bake builds both images. Build layers stay in the GitHub Actions
   cache, with one cache for each image, so later runs build only what changed.
3. `deploy/docker/check.sh` checks the images. See
   [Check the images](#check-the-images).
4. [dive](https://github.com/wagoodman/dive) checks that the image layers do not
   waste space.
5. [Trivy](https://trivy.dev) scans both images. The job fails when an image has
   a known `HIGH` or `CRITICAL` vulnerability that has a fix. Trivy does not see
   the Node.js version, because Node.js is copied into the image and not
   installed as a package.
6. The job saves both images as the `images-<commit-sha>` artifact for seven
   days.
7. For pushes, the job publishes the images. It uses the build cache, so it does
   not build again.

The workflow runs for pull requests, pushes to `main`, and tags like `v1.2.3`.
It publishes images only for pushes:

| Event               | Published tags              |
| ------------------- | --------------------------- |
| A push to `main`    | `<commit-sha>` and `latest` |
| A tag like `v1.2.3` | `<commit-sha>` and `v1.2.3` |

The images go to the GitHub container registry, at
`ghcr.io/openbot-build/openbot` and
`ghcr.io/openbot-build/openbot/protocol-test`. The workflow does not deploy
OpenBot. To use a published image with Compose, pull it and tag it as
`openbot:<tag>`.

### Publish packages

All public packages are released together with one version. `pnpm packages:pack`
sets that version in every public package, pins the dependencies between them to
it, packs them into `.release/`, and records each file's hash in
`.release/release.json`. The publishing jobs publish exactly these files and
never build again.

| Event                      | Version                    | npm tag                  | Published to            |
| -------------------------- | -------------------------- | ------------------------ | ----------------------- |
| A push to `main`           | `0.0.0-commit-<full hash>` | `sha-<full hash>`        | GitHub Packages         |
| A tag like `v1.2.3-beta.0` | `1.2.3-beta.0`             | `alpha`, `beta`, or `rc` | GitHub Packages and npm |
| A tag like `v1.2.3`        | `1.2.3`                    | `latest`                 | GitHub Packages and npm |

A prerelease tag names its channel, `alpha`, `beta`, or `rc`, followed by a
number. Its packages never become `latest`. No tag moves back to an older
version: a late upload of an older version is published under `backport`, or
under `alpha-backport`, `beta-backport`, or `rc-backport` for a prerelease.

Each registry has its own job concurrency group, `publish-github-packages` or
`publish-npm`, with `queue: max`, so two runs never publish to the same registry
at once. A rerun skips a version that already exists with the same contents, and
stops if the contents differ. Before you publish by hand, wait until the queued
publishing jobs for that registry finish.

The repository's `.npmrc` sends the `@openbot-build` scope to GitHub Packages.
The release script sets the scope's registry too, so it always publishes to the
registry you name.

To release a version:

1. Make sure `main` passes CI.
2. Tag the commit and push the tag, such as `v1.2.3` for a stable release or
   `v1.2.3-beta.0` for a prerelease:

   ```sh
   git tag v1.2.3
   git push origin v1.2.3
   ```

3. The `npm` job waits for the `npm` environment, if it requires approval, and
   then publishes.

The `npm` job uses npm's
[trusted publishing](https://docs.npmjs.com/trusted-publishers): npm accepts the
workflow run's OIDC token instead of an access token, and adds a provenance
statement to every package. No secret is stored in the repository. Each package
trusts the `ci.yml` workflow of `openbot-build/openbot` in the `npm`
environment:

```sh
npm trust github @openbot-build/client --file ci.yml --repo openbot-build/openbot --env npm --allow-publish
npm trust list @openbot-build/client
```

npm can only trust a package that exists. A maintainer therefore publishes a new
package once from the files CI packed, and trusts it afterwards:

```sh
gh run download <run id> --name packages-<commit hash> --dir .release
npm login
devenv shell -- pnpm packages:publish npm
```

### Publish a client snapshot

The workflow `.github/workflows/sdk-snapshot.yml` runs for pushes to
`codex/artifact-citation-contract`. It builds the client and the packages it
needs, checks the API and client, and packs only `@openbot-build/client`. After
those checks pass, a second job uses the repository's `GITHUB_TOKEN` to publish
the snapshot as `0.0.0-commit-<full-hash>` with a `sha-<full-hash>` tag. The
`latest` tag and the server release stay on the main release path. The
publishing job waits in the same `publish-github-packages` queue as the main
workflow.

### Publish the docs site

The workflow `.github/workflows/docs.yml` publishes the docs site to
[GitHub Pages](https://docs.github.com/pages) at
[docs.openbot.build](https://docs.openbot.build). It runs for each push to
`main`. You can also start it by hand from the Actions tab.

| Job      | What it does                                                                                                            |
| -------- | ----------------------------------------------------------------------------------------------------------------------- |
| `build`  | Runs `pnpm --filter "@openbot-build/docs..." build` in `devenv shell`. This builds the docs and the packages they need. |
| `deploy` | Sends `packages/docs/dist` to GitHub Pages.                                                                             |

The `build` job sets `DOCS_URL` to `https://docs.openbot.build`. Astro uses it
for full page links, such as the sitemap. Only one deploy runs at a time.

The repository settings must use **GitHub Actions** as the Pages source, with
`docs.openbot.build` as the custom domain. Set its DNS CNAME to
`openbot-build.github.io`. This Actions workflow does not use a `CNAME` file in
the source. The English manual starts at `/`, Chinese at `/zh-cn/`, and German
at `/de/`. The generated API reference starts at `/api/`. See
[Manage a custom domain](https://docs.github.com/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site).

### Check the images

`deploy/docker/check.sh` starts `compose.production.yaml` with test settings.
The extra file `compose.check.yaml` removes the host ports and adds a second
OpenBot node, setup, and checks. Both nodes share the database and secrets. Each
node has its own private host. The `setup` service runs after `migrate`, before
either node starts. The `check` service runs the checks. `check.env` has the
test settings. None of them are real secrets.

The `check` service runs `check.mjs` inside the Compose network, after both
OpenBot nodes and the protocol test service are healthy. It checks that:

- `/v1/chats` returns `401` with no key and with a bad key,
- `/openapi.json` works on both nodes,
- private RPC rejects missing and wrong secrets,
- each node can call the other node with the shared secret,
- the protocol test Catalog has the right public origin,
- MCP discovery on the protocol test service works.

Both nodes mount `check.plugins.yml` read only as their plugins file. It turns
`triggers` off. The script checks that the routes of triggers answer `503` with
`FeatureUnavailable` on both nodes, that the OpenAPI document still has them,
and that a write to the file fails with `EROFS`. It runs
`openbot-inspect plugins`, and checks that both nodes wrote the same manifest
hash to `openbot_execution_runners` and gave no warning about other plugins.

The script also checks an empty database, a repeated migration, both registered
runner addresses, and refusal to migrate while servers are active. Each run uses
its own Compose project. At the end, it removes that project and its test
database. Workflow recovery and node failure tests run in the package test
suite; this image check covers the production wiring.

Run the same checks on your computer:

```sh
devenv shell -- pnpm images
devenv shell -- pnpm images:check
devenv shell -- hadolint deploy/docker/Dockerfile
devenv shell -- dive --ci --source docker openbot:local
devenv shell -- trivy image --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed openbot:local
```
